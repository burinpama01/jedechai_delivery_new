🛵 StoreOS Connect Trigger — รายงานวิเคราะห์จุดกระทบ

เวอร์ชัน 1 · 19 กันยายน 2569 · หลัง fix วันเดียวกัน (realtime publication + trigger search_path)

ขอบเขต: วงจร sync ออเดอร์อาหารระหว่าง JDC ↔ StoreOS ใน 3 รูปแบบการใช้งาน — ใช้ POS อย่างเดียว / ใช้แอป JDC อย่างเดียว / ใช้ร่วมกันในวันเดียว

1) สถาปัตยกรรมปัจจุบัน (As-Is)

Outbound (JDC → StoreOS) — trigger 2 ตัวบน Postgres ยิง webhook ผ่าน net.http_post (fire-and-forget):

  • trg_notify_storeos_order_created (บน booking_items INSERT) → หัวข้อ order.created พร้อมรายการอาหาร + commission (GP) — กันยิงซ้ำด้วย pos_order_created_at
  • trg_notify_storeos_order (บน bookings INSERT / UPDATE OF status) → หัวข้อ order.status — เฉพาะออเดอร์ food, ข้ามถ้าสถานะไม่เปลี่ยน, ข้ามถ้า status_origin='storeos' (กัน echo loop)

Inbound (StoreOS → JDC) — Edge Functions 3 ตัว, ทุกตัวตรวจ Connection Key + HMAC + timestamp (±5 นาที) + dedup event_id (ซ้ำ → 409):

  • connect_upsert_menu — แก้เมนู/option บน POS แล้ว sync เข้า JDC
  • connect_set_shop_status — เปิด/ปิดร้านจาก POS (profiles.shop_status)
  • connect_update_order_status — รับได้เฉพาะ preparing / ready_for_pickup; ready วิ่งเข้า mark_food_ready_guarded (logic เดียวกับปุ่ม "อาหารพร้อม" ในแอป) + optimistic lock (เลขสถานะไม่ตรง → 409)

ตัวกำกับทิศทาง (echo governor) — คอลัมน์ status_origin: ทุก inbound ตั้งเป็น 'storeos' (trigger ขาออกจะเงียบ), accept_booking/complete_booking รีเซ็ตเป็น 'jdc' (ฝั่งคนขับเป็นเจ้าของสถานะใหม่ → แจ้ง POS ต่อได้)

ออเดอร์ 1 ใบในวันที่ใช้ร่วมกัน (กรณ์จริง 16 ก.ย.) ลูกค้าสั่งในแอป ──► bookings(pending_merchant) ──► order.created → POS ร้านกด POS: preparing ──► inbound ──► bookings(preparing, origin=storeos) ──► ✕ ไม่ echo ร้านกด POS: พร้อม ──► mark_food_ready_guarded(origin=storeos) ──► ✕ ไม่ echo / แจ้งคนขับ คนขับรับงาน ──► accept_booking ──► bookings(driver_accepted, origin=jdc) ──► order.status → POS คนขับส่งเสร็จ ──► complete_booking(origin=jdc) ──► order.status → POS ลูกค้ายกเลิก ──► cancel_wallet_booking_with_refund ──► bookings(cancelled, origin ค้างเดิม!)

2) สถานการณ์ A — วันที่ใช้แอป JDC อย่างเดียว

ผลลัพธ์: ผ่านทุกขั้น (หลัง fix 19 ก.ย.) — POS ทำหน้าที่เป็น "จอแสดงออเดอร์" ของร้าน: ทุกการเปลี่ยนสถานะจากฝั่งแอป (ร้านรับ / คนขับรับ / ส่งเสร็จ / ลูกค้ายกเลิก) ถูก push ไป POS ครบ เพราะ origin เป็น jdc/NULL เสมอ
  • ก่อน fix 19 ก.ย.: พัง ลูกค้ายกเลิกไม่ได้ (hmac 42883 ใต้ RPC ที่ pin search_path) และ แอดมิน force-cancel ก็พังด้วยเหตุผลเดียวกัน (ยังไม่เคยชนเพราะไม่มีใคร force-cancel ออเดอร์ food ตอน connection active)
  • การจ่ายด้วย Wallet ไม่กระทบ — RPC แตะแค่ payment_method ไม่ใช่ status trigger ไม่ยิง
  • Laundry/parcel/ride ไม่กระทบ — trigger ออกทันทีถ้าไม่ใช่ food

3) สถานการณ์ B — วันที่ใช้ StoreOS เป็นหลัก

สิ่งที่ทำได้จาก POS: ดูออเดอร์เข้าแบบเรียลไทม์ · กด preparing/พร้อมส่งมอบ · แก้เมนู · เปิด/ปิดร้าน — ทั้งหมด sync เข้า JDC ถูกต้อง (มี dedup + optimistic lock กันกดซ้ำ/ชนกัน)

ข้อจำกัดเชิงสถาปัตยกรรม (F3): รับออเดอร์ "ใหม่" ทาง POS ไม่ได้ — ไม่มี inbound order.created จาก StoreOS (connect_update_order_status ตอบ 404 ถ้าไม่มี booking) ออเดอร์ทุกใบต้องเกิดที่แอป JDC เท่านั้น ถ้าร้านรับสายโทรเข้าแล้วพิมพ์เข้า POS เอง JDC จะไม่รู้จักออเดอร์นั้น → ไม่มีคนขับรับงาน → ต้องมีใครสั่งซ้ำผ่านแอป JDC เสมอ

4) สถานการณ์ C — วันที่ใช้ร่วมกัน (สลับกันจับ)

วงจรหลักผ่านครบ — พิสูจน์ด้วยข้อมูลจริง 16 ก.ย.: inbound 3 events (08:16–08:18) + คนขับรับ/ส่งสำเร็จ + POS ได้รับทุก order.status จากฝั่ง JDC

4.1 จุดชนที่ออกแบบไว้ดีแล้ว (กันชนได้)

จุดชนกลไกป้องกันผลลัพธ์
กด "อาหารพร้อม" ในแอป กับกด ready บน POS พร้อมกันสองทางใช้ mark_food_ready_guarded เดียวกัน + FOR UPDATE + เช็คสถานะก่อนเปลี่ยนฝั่งหลังได้ no_op/409 — idempotent ไม่พัง
StoreOS ยิง webhook ซ้ำ (retry)event_id unique + ตรวจ timestamp ±5 นาทีซ้ำได้รับ 409 Duplicate — สถานะไม่เพี้ยน
POS เปลี่ยนสถานะ แล้ว JDC เปลี่ยนตาม วนกลับไป POS วนไม่รู้จบstatus_origin governor (inbound ติดธง storeos → ขาออกเงียบ; คนขับรับ/จบ รีเซ็ต jdc)ไม่เกิด echo loop
สถานะบน POS ล้ำหน้า JDC (เช่น ยืนยันก่อนร้านกดในแอป)transitions map เข้ม: จาก pending_merchant/accepted → preparing เท่านั้นทะเลาะกันไม่ได้ 409 พร้อมบอกสถานะปัจจุบัน

4.2 จุดกระทบคงเหลือ (ยังเปิด)

#จุดกระทบความรุนแรงรายละเอียด
F2 ยกเลิกออเดอร์แล้ว POS ไม่รู้ (เมื่อ origin ค้าง storeos) สูง cancel_wallet_booking_with_refund และ admin_force_cancel_booking_with_wallet_refund ไม่เซ็ต status_origin → ถ้าการเปลี่ยนสถานะล่าสุดมาจาก POS (เช่น ร้านกด preparing) origin จะค้าง storeos → ขาออกเงียบ → POS ยังโชว์ออเดอร์เป็นงานมีชีวิต ทั้งที่ JDC ยกเลิกไปแล้ว (ร้านอาจทำอาหารเปล่า)
F4 Outbound fire-and-forget ไม่มี retry / delivery log กลาง net.http_post ไม่มีการบันทึกผลส่ง — StoreOS ล่ม/เน็ตหลุดช่วงใด event นั้นหายเงียบ ไม่มีใครรู้จากฝั่ง JDC (คิว pg_net ปัจจุบัน = 0 คือถูก drain หมด แต่ "ถูกยิงทิ้ง" ไม่เท่ากับ "StoreOS ได้รับ")
F5 Connection เป็น system-wide → ออเดอร์ทุกร้านไป POS กลาง เงื่อนไขคือ merchant_id IS NULL (system-wide) → ออเดอร์อาหารของทุกร้านในระบบถูก push ไป StoreOS ด้วย merchant_id ของตัวเอง — ร้านที่ StoreOS ไม่รู้จักต้องถูกฝั่ง StoreOS ignore เอง ถ้าไม่ ignore จะเกิดออเดอร์ขยะใน POS
F8 เปิด/ปิดร้านสองทาง last-write-wins ต่ำ-กลาง POS ตั้ง shop_status ได้ แอป merchant ก็ตั้งได้ — ไม่มี sync สถานะปัจจุบันกลับไปฝั่งตรงข้าม สองจออาจโชว์สถานะต่างกันชั่วคราวจนกว่าจะมีคนกดใหม่
F9 115 ออเดอร์เก่า origin=NULL ต่ำ ออเดอร์ก่อนมีคอลัมน์ status_origin เป็น NULL → ขาออกยิงปกติ (NULL ≠ 'storeos') — พฤติกรรมถูกต้อง แค่บันทึกไว้ให้เข้าใจตรงกัน

6) ข้อเสนอแนะ (ยังไม่ได้แก้ — รอผู้ใช้ตัดสินใจ)

  1. ปิดช่อง F2 (แนะนำทำก่อน): เพิ่ม status_origin='jdc' ใน UPDATE ของ cancel_wallet_booking_with_refund และ admin_force_cancel_booking_with_wallet_refund — บรรทัดเดียวต่อฟังก์ชัน ผล: ทุกการยกเลิกจากฝั่ง JDC บอก POS เสมอ ไม่ว่า origin เดิมจะเป็นอะไร
  2. ลด F4: เก็บ log outbound event ลงตาราง (หรืออ่านจาก net.http_request_queue ช่วงสั้นๆ) + มีหน้า admin ดู "event ล่าสุดที่ยิงไป StoreOS" เพื่อสังเกตุว่า sync ตายตอนไหน — ไม่จำเป็นต้อง retry engine เต็มรูปแบบในเฟสนี้
  3. กัน F5 ระดับ data: เพิ่มตาราง mapping ร้าน JDC ↔ ร้าน StoreOS แล้วให้ trigger push เฉพาะร้านที่ลงทะเบียน (เปลี่ยนจาก system-wide เป็น per-merchant) — ทำเมื่อมีร้านเข้าใช้จริงมากกว่า 1-2 ร้าน
  4. F3 (รับออเดอร์ทาง POS): ถ้าธุรกิจต้องการ ต้องเพิ่ม inbound order.created + การ map เมนู/ลูกค้า walk-in — เป็น feature ใหม่ ไม่ใช่ bug fix ควรทำเป็นแผนแยก
  5. ทดสอบประจำ: เพิ่ม E2E สถานการณ์ C (POS preparing → cancel → เช็คว่า POS ได้รับ cancelled) เข้า smoke ทันทีที่ทำข้อ 1
