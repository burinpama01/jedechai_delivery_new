1) สถาปัตยกรรมปัจจุบัน

โครงสร้าง wallets (user_id, balance) ← balance เป็น "ค่าที่แสดง" ไม่ได้ derive จาก ledger wallet_transactions (type, amount, related_booking_id) ← ledger บันทึกทุกการเคลื่อนย้าย withdrawal_requests ← schema+RLS พร้อม แต่ยัง 0 รายการ การขยับเงิน "ควร" ผ่าน RPC ทั้ง 3 ตัว (SECURITY DEFINER): wallet_topup(user, amount, desc, type, booking) เครดิต + บันทึก ledger wallet_deduct(user, amount, desc, type, booking) เดบิต + บันทึก ledger wallet_adjust(user, amount, desc) ปรับแบบมี ledger type ที่ใช้จริง: topup ×14 · commission ×41 · admin_adjustment ×9 (+977,620!) · payment ×1 · hold/release ×1 · laundry_payout ×1 · invalid_refund(±) ×9

สิ่งที่ออกแบบดีและทำงานจริง

  • ทุกการขยับเงินมี ledger + อ้างอิง booking: RPC ทั้งสามบังคับ type + description + related_booking_id — ตรวจสอบย้อนได้
  • Laundry คือ reference implementation ครบวงจร: payment (−6) → hold ค่าส่งขากลับ (−1) → release (+1) → laundry_payout คนขับ (+5.50) — ทุกบาทมีที่มีที่ไป
  • ค่าคอมมิชชันหักอัตโนมัติตอน complete: 41 รายการ ตรงกับ driver_earnings/app_earnings บน booking
  • Topup ผ่านสลิกมี pipeline: topup_requests → ตรวจสลิก → เครดิต (14 รายการ รวม ฿24,660)
  • RPC ชำระเงินลูกค้า (customer_wallet_pay_booking) validate ยอดฝั่ง server จาก booking จริง (แก้ไปแล้วรอบ มิ.ย.)
  • RLS ฝั่งอ่านถูกต้อง: เห็นกระเป๋า/ประวัติของตัวเองเท่านั้น + แอดมินเห็นทุกอย่าง

2) ช่องโหว่ / ปัญหาที่พบ

W2 — ผู้ใช้ "ตั้งยอดกระเป๋าตัวเอง" ได้ผ่าน API โดยตรง CRITICAL · ใช้ได้เลยตอนนี้

RLS เปิดให้เขียนโดยตรง: policy wallets_update_own ให้ UPDATE wallets แบบ WITH CHECK = null (ไม่จำกัดคอลัมน์/ค่า) และ wallet_tx_insert ให้ INSERT wallet_transactions ของกระเป๋าตัวเองได้ → ผู้ใช้เรียก PostgREST ตรงๆ: update wallets set balance = 999999 where user_id = ตัวเอง ได้ทันที ไม่มี trigger กัน (มีแค่ trigger อัปเดต updated_at) ตรวจแล้ว: แอปไม่ได้เขียนทางนี้เลย (WalletService ใช้ RPC ล้วน — grep ทั้ง repo) → policy เหล่านี้คือพื้นผิวโจมตีล้วนๆ ปิดทิ้งได้เลยไม่กระทบอะไร · คลาสเดียวกับ policy "Allow all selects/updates on bookings" ที่พบไว้ก่อนหน้า — โปรเจคมี policy หลวมตกค้างหลายจุด ควรรีวิวทั้ง schema รอบเดียว

W1 — ออเดอร์ food/ride/parcel ที่ "จ่า่ยด้วย Wallet": เงินลูกค้าหายเงียบ คนขับไม่มีทางได้เงิน CRITICAL (latent) · UI เข้าถึงได้ทุกบริการ

เส้นเงินวันนี้: ลูกค้ากดจ่ายด้วย Wallet (มีใน checkout ของ food + payment_screen ใช้ได้ทุก service) → customer_wallet_pay_booking เดบิตกระเป๋าลูกค้า → จบ. ไม่มีโค้ดไหนเครดิตคนขับอีกเลย (complete_booking มีแค่ "หัก commission จากกระเป๋าคนขับ"; ledger ไม่มี type จ่ายคนขับสำหรับ non-laundry เลย — laundry_payout มีเฉพาะทางซักผ้า) ถ้าเกิดจริง: คนขับส่งเสร็จ ไม่ได้เงินจากลูกค้า (จ่าย wallet แล้ว) ไม่ได้เครดิตจากระบบ แถมถูกหัก commission จากกระเป๋าตัวเอง และยังต้องจ่ายร้านเงินสด → ขาดทุนเต็มยอด ยังไม่เคยเกิดจริง (ใน production มีออเดอร์ wallet แค่ 2 ใบ เป็น laundry ทดสอบเดือน มิ.ย.) — แต่เมนูเปิดใช้ได้อยู่ทุกวันนี้
ตอบคำถามเปิดของแผนคูปองแล้ว: เงื่อนไขชดเชยส่วนลด "เฉพาะเงินสด/โอน" ถูกต้อง — และยิ่งไปกว่านั้น: ห้ามกระตุ้นให้ใช้ wallet กับ food ก่อนแก้ W1

4) ข้อเสนอ (เรียงตามความเร่ง)

  1. W2 — ปิด policy เปิดวางทันที (migration เล็ก งาน 15 นาที): DROP policy wallets_update_own + wallet_tx_insert (+ policy ซ้ำเดิม "Users can insert own transactions" / "Users can update own wallet balance") — เหลือไว้เฉพาะ SELECT own + admin; การเขียนทุกทางผ่าน RPC อย่างเดียว (แอปไม่กระทบ — ตรวจแล้วไม่มี direct write) · แนะนำรีวิว policy หลวมทั้ง schema พร้อมกัน (เช่น bookings "Allow all" ที่รายงานไว้ก่อนหน้า)
  2. W1 — ปิดกั้นชั่วคราวก่อน แล้วแก้ถาวร:
    • ทันที: ซ่อนตัวเลือก "จ่ายด้วย Wallet" ใน checkout food/ride/parcel (เหลือ laundry ที่ปิดวงจรแล้ว) — หรือยอมรับความเสี่ยงต่ำชั่วคราวเพราะยังไม่มีใครใช้
    • ถาวร: ตอน complete_booking ของ non-laundry ที่ payment_method='wallet' → เครดิตคนขับ driver_earnings (type ใหม่ เช่น job_payout) — จุดเดียวกับที่แผนคูปอง (ข้อ A) และแผนรวม (G2) จะแก้ → รวม migration ทั้งสามแผนเป็นจุดเดียวได้ · พร้อมกันนั้นต้องตอบ: ร้านได้เงินยังไงใน wallet order (คนขับจ่ายสดที่ร้านแล้วระบบคืนให้? หรือรอมีกระเป๋าร้าน — W6)
  3. W3 — reconciliation job: cron เทียบ balance กับ sum(ledger) ทุกกระเป๋า + แจ้งแอดมินเมื่อเพี้ยน + ซ่อม 3 กระเป๋าปัจจุบันด้วย ledger ปรับแต่งที่มี description ชัดเจน
  4. W4 — แยกเงินทดสอบ: tag ledger admin_adjustment ที่เป็นเงินทดสอบ / หรือปรับเป็นศูนย์ด้วยรายการ reverse ที่อธิบายเหตุผล ก่อนรายงานการเงินจริง
  5. W5 — E2E ถอนเงินก่อนเปิดใช้จริง (ขอ→อนุมัติ→เดบิตจริง→สถานะ)
สรุปหนึ่งบรรทัด: แกนกลาง (RPC+ledger+laundry วงจรเต็ม) แข็งแรง — แต่ policy เขียนตรงคือประตูเปิด (W2 ปิดได้เลยวันนี้) และ wallet payment ของบริการทั่วไปยังเป็น "ท่อตัน" ที่เงินลูกค้าเข้าแล้วไม่ถึงใคร (W1) ซึ่งผูกกับแผนคูปอง/แผนรวมที่จุด complete_booking จุดเดียวกัน
