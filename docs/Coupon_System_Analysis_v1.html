🎟️ วิเคราะห์ระบบคูปอง — ใช้จริง 10 ครั้ง พบปัญหาเงินจริง 3 เรื่อง + เครื่องไม้เครื่องมือที่ออกแบบไว้แต่ไม่เคยถูกใช้

เวอร์ชัน 1 · 19 กันยายน 2569 · วิเคราะห์จากโค้ดทั้งเส้น (สร้าง → แจก → ใช้ → settle) + ข้อมูลจริง: คูปอง 7 ใบ, การใช้ 10 ครั้ง (6 ถูกยกเลิก), grant 13 รายการ

1) สถาปัตยกรรมปัจจุบัน

วงจรคูปอง แอดมิน/ร้านสร้าง ──► coupons (funding_source, discount_base, GP rates, stacking_group, │ driver_compensation_policy … ครบเครื่องใน schema) ├─ code_only ──► ลูกค้าพิมพ์โค้ดที่ checkout ├─ claimable ──► claim_coupon RPC ──► user_coupons (claimed) ──► เลือกที่ checkout └─ auto_grant ──► trigger (welcome/referral) ──► user_coupons อัตโนมัติ ตอนสั่ง: client คำนวณส่วนลด (Coupon.calculateDiscount) ──► จ่ายลดราคาไปก่อน หลังสร้าง booking: apply_coupon_atomic (FOR UPDATE + เช็ควัน/ลิมิต server) ──► coupon_usages + used_count ⚠️ ตอนยกเลิกออเดอร์: ไม่มีอะไรแตะคูปองเลย — ใช้ไปแล้วหายถาวร

สิ่งที่ออกแบบ/ทำงานได้ดี

  • apply_coupon_atomic ป้องกัน race ได้จริง: FOR UPDATE ล็อกแถว + ตรวจวันหมดอายุด้วย now() ฝั่ง server (กันนาฬิกาเครื่องปลอม) + ลิมิตรวม/รายคนแบบ atomic
  • RLS แน่นพอ: ลูกค้าเห็นเฉพาะคูปอง active / ร้านจัดการได้เฉพาะของตัวเอง (merchant_id = auth.uid()) / ประวัติการใช้เห็นเฉพาะเจ้าของ+แอดมิน
  • โมเดลรองรับครบ: 3 ประเภท (fixed/percentage/free_delivery) + เพดานส่วนลด + ฐานส่วนลด (subtotal/delivery_fee) + ขั้นต่ำ + เฉพาะร้าน/เฉพาะบริการ
  • คูปองระบบซ่อนรายละเอียดจากร้าน (hideSystemCouponBreakdown) ส่วนคูปองร้านฝังในโน้ตให้ร้านเห็น

2) ปัญหาที่มีหลักฐานเกิดขึ้นจริงแล้ว

C1 — ใครแบกส่วนลด: คำตอบจริงคือ "คนขับ" (ทั้งที่ DB บอกว่าร้านแบก) เกิดแล้ว · เงินจริง

ออเดอร์ 25 พ.ค. (Patty, เงินสด, ใช้ NEWUSER01 ส่งฟรี): อาหาร 110 + ค่าส่ง 25 − ส่วนลด 25 → ลูกค้าจ่าย 110 ระบบจองค่าจ้างคนขับ 28 (ค่าส่ง 25 + GP 3) แต่เงินสดจริง: เก็บ 110 → จ่ายร้าน 98 → เหลือ 12 − ถูกหักกระเป๋าฝั่งแอป 9 = เหลือ 3 คนขับขาดจริง 25 บาท = ค่าส่งทั้งก้อน ทั้งที่คูปองระบุ funding_source='merchant' — เพราะ ไม่มีโค้ดไหนอ่าน funding_source / merchant_gp_charge_rate / driver_compensation_policy เลย (grep ทั้ง repo: มีแค่ model เก็บค่า ไม่มี settlement/ledger ใช้) นี่คือ G3 ในแผนรวม — ตอนนี้มีหลักฐานเกิดจริงแล้ว 4 ออเดอร์ที่ completed ด้วยคูปอง (10 ก.พ., 1 พ.ค., 25 พ.ค., 27 พ.ค.)

C2 — ยกเลิกออเดอร์แล้วคูปอง "ไหม้" ทันที เกิดแล้ว 6 จาก 10 ครั้ง

cancel_wallet_booking_with_refund ไม่แตะคูปองเลย (ตรวจ function จริงแล้ว): แถว coupon_usages ค้าง + used_count ไม่ลด + per_user_limit ถูกนับแล้ว ผลจริง: 6 ออเดอร์คูปองถูกยกเลิก → ลูกค้า 6 คนใช้ NEWUSER01 (จำกัด 1 ครั้ง/คน) ไม่ได้อีกตลอดชีวิต แม้สั่งไม่สำเร็จ ยิ่งถ้าคูปองแคมเปญหน้าใหญ่ + อัตรายกเลิกสูง = คูปองถูกเผาโดยออเดอร์ที่ไม่เกิดขึ้นจริง

C3 — จำนวนส่วนลดคำนวณฝั่ง client แล้ว "บอก" server ตรงๆ ช่องโหว่ integrity

apply_coupon_atomic(p_discount_amount) — server บันทึกจำนวนที่ client ส่งมาโดยไม่คำนวณซ้ำ สิ่งที่ RPC ตรวจ: active / วันที่ / ลิมิตรวม / ลิมิตรายคน — ไม่ตรวจ: จำนวนส่วนลด, ขั้นต่ำ, ประเภทบริการ, ร้านที่กำหนด (สี่อย่างนี้เช็คแค่ client) client ดัดแปลง (หรือแอปเวอร์ชันเก่า logic เก่า) ส่งส่วนลด ฿0.01 หรือเกินเพดานได้ — wallet payment RPC ฝั่งนี้ validate จาก server แล้ว แต่คูปองยังไม่

5) วิธีแก้ — เสนอเพิ่มเข้าแผนรวม (ขยาย Phase 2/4)

  1. C2 (แก้ก่อน ง่ายและถูก): ใน cancel RPC (ตัวเดียวกับที่จะแก้ F2 ใน Phase 2 อยู่แล้ว) — เมื่อยกเลิกออเดอร์ที่มี coupon_usages: ลบแถว usage + used_count - 1 + คืนสถานะ user_coupons (claimed) — ออเดอร์ที่กลับมา completed ภายหลังจะได้คูปองคืนพร้อมใช้ใหม่
  2. C3 (คู่กับ G2 ใน Phase 2): ย้าย calculateDiscount ลง server — apply_coupon_atomic คำนวณจำนวนเองจาก coupon + booking (subtotal/delivery_fee/min_order/service/merchant ตรวจครบ) แทนการรับ p_discount_amount
  3. C1 = G3 (Phase 4 แต่ยกระดับความเร่ง): เลือกนโยบายแล้ว implement จริง — ตัวเลือกที่เป็นไปได้:
    • (ก) platform แบก: หักมูลค่าส่วนลดออกจาก GP ระบบก่อนแบ่ง (เหมาะกับคูปอง platform เช่น WELCOME20)
    • (ข) merchant แบก: ลด merchantReceives ลงเท่าส่วนลด (ตามที่ funding_source='merchant' เขียนไว้ — เหมาะกับ NEWUSER01/คูปองร้าน) แล้วคนขับได้ค่าจ้างครบตามจอง
    • (ค) ใช้ driver_compensation_policy ที่มีอยู่: ตอน complete เติมกระเป๋าคนขับชดเชยเท่าส่วนลดโดยเด้งไปที่ funding_source ปลายทาง
  4. C4: เปลี่ยนทุกจุดเปรียบเทียบวันที่คูปองให้เป็น timestamptz จริง (ส่ง Z/offset จาก client หรือย้ายการกรองไป RPC ที่ใช้ now()) — ทำคู่กับ Phase 1 ได้
  5. C5: หน้า checkout ดัน "คูปองของคุณ" ที่ claim ไว้ขึ้นมาก่อนช่องกรอกโค้ด + แจ้งเตือนก่อนหมดอายุ
สรุปหนึ่งบรรทัด: ระบบคูปอง "กันไว้" ดี (atomic, RLS, ลิมิต) แต่สามฝั่งเงินยังไม่ปิด — ตอนนี้มีหลักฐานแล้วว่าคนขับจ่ายค่าส่งฟรีแทนร้านจริง 4 ออเดอร์ และคูปองไหม้จากการยกเลิก 6 ครั้ง · แนะนำเสริม C2/C3 เข้า Phase 2 ของแผนรวม และยก G3=C1 ขึ้นมาตัดสินใจนโยบายจริง
