Implementation Plan: ระบบเสนอออเดอร์ให้คนขับทีละคน

26 กันยายน 2026 · สถานะ: กำลังดำเนินการในเครื่อง

เป้าหมาย: เสนอคนขับว่างที่ใกล้ที่สุดทีละคน 60 วินาที พร้อมปุ่มข้ามงานและเสียงซ้ำขณะแอปอยู่ด้านหน้า โดยทุกสถานะข้อเสนอถูกตัดสินฝั่งฐานข้อมูล

1. ฐานข้อมูลและการแข่งขัน

สร้าง migration ใหม่ใน supabase/migrations/ สำหรับตาราง driver_job_offers, unique partial indexes ที่ป้องกัน active offer ซ้ำต่อ booking และ driver, RLS, และ RPC สำหรับสร้างข้อเสนอ รับ ข้าม หมดเวลา และมอบหมายโดยแอดมิน

  • เขียนการทดสอบ SQL หรือ smoke test ที่พิสูจน์ว่า driver อื่นรับข้อเสนอไม่ได้, กดรับหลังหมดเวลาไม่ได้, กดข้ามแล้วส่งต่อทันที, และหลายออเดอร์ไม่เลือก driver คนเดียวกัน
  • รันทดสอบก่อนแก้ให้เห็น failure แล้วแก้จนผ่าน
  • ยืนยันว่า accept_booking เดิมไม่เปิดทางข้ามคิวและไม่รับ p_driver_id ของผู้อื่น

2. Worker และ push

สร้าง Edge Function ประมวลผลข้อเสนอที่ครบเวลาและงานค้างเป็น batch แบบ idempotent; เชื่อม FCM เดิมด้วย service-role ฝั่ง server เท่านั้น และบันทึกผลส่งเพื่อ retry ไม่ส่งซ้ำแบบไม่จำกัด

  • ตั้ง schedule ฝั่ง server ให้เดินคิวเป็นระยะ ไม่อาศัยหน้าแอดมินหรือแอปคนขับเปิดอยู่
  • ทดสอบกรณี FCM ล้มเหลว, worker รันซ้ำ และไม่มี driver ที่เข้าเกณฑ์

3. แอปคนขับ

แก้ driver_dashboard_screen.dart และ booking_service.dart ให้ดึงเฉพาะงานที่มอบหมายให้ตนหรือข้อเสนอ active ของตน แสดงเวลาคงเหลือและปุ่มรับ/ข้าม และหยุดเสียงทันทีเมื่อข้อเสนอสิ้นสุด

  • ใช้ flutter_ringtone_player ที่มีอยู่สำหรับเสียงซ้ำขณะแอปอยู่ด้านหน้า; background ใช้ช่อง FCM งานคนขับเดิม
  • เพิ่ม widget/service tests สำหรับ visibility, countdown, skip และ lifecycle ของเสียง
  • หากจำเป็นต้อง build ให้ bump pubspec.yaml ก่อน ตามกฎโปรเจกต์

4. แอดมินและเส้นทางเดิม

ปิด timer auto dispatch ใน admin-web/app.legacy.js และให้หน้าแผนที่อ่านสถานะคิวจาก server; การมอบหมายเองผ่าน RPC แบบ conditional เท่านั้น ไม่ update booking โดยตรง

  • ทดสอบว่าแอดมินไม่ทับงานที่คนขับรับไปแล้ว และปิดหน้าแอดมินแล้วคิวยังเดิน
  • ตรวจ scheduled/laundry/food/ride/parcel ว่าเริ่มคิวเฉพาะสถานะที่เหมาะสม

5. Verification และ release gate

รัน targeted SQL/Node/Flutter tests, analyze, ทดสอบ burst และให้ code_reviewer ตรวจ diff จากนั้นบันทึก Obsidian log/issue/current; migration, Edge deploy, mobile build และ production deploy เป็น gate แยกตามผลตรวจ
