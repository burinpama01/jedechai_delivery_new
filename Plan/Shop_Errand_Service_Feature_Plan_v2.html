1.2 รูปแบบเวลาเปิด-ปิด

{
  "mon": [{"open":"08:00","close":"20:00"}],
  "tue": [{"open":"08:00","close":"20:00"}],
  ...
  "sun": [],                                  // ปิดทั้งวัน
  "sat": [{"open":"08:00","close":"12:00"},
          {"open":"15:00","close":"20:00"}]   // ปิดพักกลางวัน รองรับหลายช่วง
}
เรื่อง timezone: เก็บเป็นเวลาท้องถิ่น (Asia/Bangkok) แล้วเทียบด้วย now() AT TIME ZONE 'Asia/Bangkok' เสมอ — บทเรียนจาก Batch 2 เรื่อง coupon timezone ที่เคยคำนวณผิด ห้ามเทียบกับ now() ดิบ ๆ

รองรับร้านที่ปิดข้ามเที่ยงคืน (เช่น 18:00–02:00) ด้วยการให้ close < open หมายถึงข้ามวัน

1.3 RPC ค้นหาร้านในรัศมี

shop_nearby_stores(p_lat, p_lng, p_category default null)
  => คืน: id, name, category, address, lat, lng, distance_km,
          is_open_now, next_open_at, issues_receipt, photo_url

  กรอง: is_active = true
        AND distance_km <= COALESCE(store.service_radius_km, config.shop_store_radius_km)
  เรียง: ร้านที่เปิดอยู่ก่อน แล้วเรียงตามระยะทาง
ทำไมคำนวณ is_open_now ที่ server ไม่ใช่ที่แอป: นาฬิกาเครื่องลูกค้าตั้งเองได้ ถ้าคำนวณที่แอปคนที่ตั้งเวลาเครื่องย้อนหลังจะสั่งร้านที่ปิดอยู่ได้ — ฝั่ง server เป็นแหล่งความจริงเดียว

1.4 บังคับ "ร้านปิดเลือกไม่ได้" 2 ชั้น

ชั้นทำอะไร
UI (แอปลูกค้า)การ์ดร้านที่ปิดแสดงแบบจาง กดไม่ได้ พร้อมป้าย "ปิดอยู่ · เปิดอีกครั้ง 08:00 พรุ่งนี้"
Server (RPC)create_shop_booking() เช็ค is_open_now ซ้ำ ถ้าปิดให้คืน error: 'store_closed' พร้อม next_open_at
ทำไมต้อง 2 ชั้น: ซ่อนปุ่มอย่างเดียวกันคนที่เรียก API ตรงไม่ได้ และยังมีช่องว่างเวลาปกติด้วย — ลูกค้าอาจเปิดหน้าไว้ตอน 19:59 แล้วกดสั่งตอน 20:01 หลังร้านปิดไปแล้ว การเช็คซ้ำตอนสร้างออเดอร์ปิดช่องนี้

3AI อ่านใบเสร็จ

ทำเป็น edge function ใหม่ extract-shop-receipt โดยยึดโครงเดียวกับ verify-topup-slip ที่มีอยู่แล้ว (rate limit, จำกัดขนาดรูป, ตรวจชนิดไฟล์, คิว manual review)

3.1 สถาปัตยกรรม

แอปคนขับ  --(รูปบิล)-->  Supabase Storage (bucket: shop-receipts)

3.2 การเรียก Claude

  • Model: claude-opus-5
  • Input: รูปบิลแบบ base64 + prompt ภาษาไทยบอกให้ดึงยอดรวม ร้าน วันเวลา และรายการสินค้า
  • Output: ใช้ structured output (output_config.format) บังคับ schema ไม่ต้องมา parse ข้อความเอง
schema ที่ต้องการกลับมา:
{
  total_amount: number | null,      // ยอดรวมที่ต้องจ่าย
  store_name:   string | null,
  purchased_at: string | null,      // ISO ถ้าอ่านได้
  line_items:   [{ name, qty, price }],
  confidence:   "high" | "medium" | "low",
  unreadable_reason: string | null  // เบลอ / มืด / ไม่ใช่ใบเสร็จ
}
ข้อควรรู้เรื่อง API (เช็คแล้วกับ reference ปัจจุบัน): ใช้ output_config: {format: ...} ไม่ใช่ output_format ที่เลิกใช้แล้ว · thinking ใช้ {type:"adaptive"} ไม่ใช่ budget_tokens (ส่งไปจะได้ 400) · assistant prefill ใช้ไม่ได้แล้วบน model รุ่นนี้

3.3 AI เป็นผู้ช่วย ไม่ใช่ผู้ตัดสิน

ห้ามให้ AI ตัดเงินเองโดยตรง เพราะอ่านผิดได้ (บิลเบลอ บิลยับ แสงสะท้อน ร้านใช้ฟอร์มแปลก) และเป็นทางให้คนขับลองยิงรูปหลอกระบบ กฎการใช้ผลลัพธ์:

กรณีระบบทำอะไร
AI อ่านได้ + ตรงกับที่คนขับกรอก (ต่างไม่เกิน tolerance)ผ่านอัตโนมัติ ไปขั้นถัดไป
AI อ่านได้ แต่ต่างจากที่คนขับกรอกแสดงให้คนขับเห็นทั้ง 2 ยอด ให้ยืนยัน/แก้ แล้วเข้าคิวแอดมินตรวจ
AI อ่านไม่ออก / confidence ต่ำใช้ยอดที่คนขับกรอก แล้วเข้าคิวแอดมินตรวจ — ไม่บล็อกงาน ลูกค้าไม่ควรต้องรอเพราะ AI อ่านบิลไม่ออก
Claude API ล่ม / timeoutบันทึก ai_extract.status='failed' แล้วไปต่อด้วยยอดคนขับ — ห้ามให้ทั้งระบบหยุดเพราะ AI ล่ม

3.6 ความปลอดภัยของ edge function

  • API key เก็บใน Supabase secrets เท่านั้น ห้ามอยู่ในแอป — บทเรียนจากเหตุ ENV secret leak ที่ผ่านมา
  • ตรวจว่าผู้เรียกคือคนขับที่ถูก assign งานนั้นจริง ไม่ใช่แค่ login แล้วเรียกได้
  • rate limit ต่อคนขับ กันยิงรูปรัว ๆ จนค่า API บาน
  • เก็บ usage (token เข้า/ออก) ทุกครั้งเพื่อดูต้นทุนจริงและจับการใช้ผิดปกติ
  • รูปบิลเป็นข้อมูลส่วนบุคคล — bucket ต้องไม่ public, ให้เข้าถึงผ่าน signed URL เท่านั้น

4ร้านที่ไม่มีใบเสร็จ: ยืนยันด้วยรูปสินค้า

ตลาดสด ร้านโชห่วย แผงลอย ส่วนใหญ่ไม่ออกใบเสร็จ ใช้ shop_stores.issues_receipt เป็นตัวตัดสินว่าจะใช้ flow ไหน

4.1 เปรียบเทียบ 2 โหมด

ร้านมีใบเสร็จร้านไม่มีใบเสร็จ
คนขับทำอะไรถ่ายใบเสร็จ 1 รูปถ่ายรูปสินค้าที่ซื้อ (1 รูปรวม หรือรายชิ้น) + กรอกราคาต่อชิ้น
ใครตรวจยอดAI อ่านแล้วเทียบอัตโนมัติลูกค้ายืนยันเอง
ไปขั้นถัดไปเมื่อยอดตรง toleranceลูกค้ากดยืนยันในแอป
ถ้าไม่ผ่านเข้าคิวแอดมินลูกค้าทักแชทคุยกับคนขับ หรือเข้าคิวแอดมิน

4.2 Flow โหมดรูปสินค้า

คนขับซื้อของ→ ถ่ายรูปสินค้า + กรอกราคา→ ส่งให้ลูกค้า (สถานะ receipt_review)→ ลูกค้าเห็นรูป + ยอด→ กดยืนยัน→ คนขับส่งของ

4.3 คำถามสำคัญ: ถ้าลูกค้าไม่กดยืนยัน?

เป็นจุดที่ระบบค้างได้ง่ายที่สุด เพราะของซื้อไปแล้ว คนขับรออยู่หน้าร้าน ถ้าปล่อยให้รอไม่มีกำหนดคือการลงโทษคนขับ ข้อเสนอ:

  • แจ้งเตือน push ทันทีที่ส่งรูป + แจ้งซ้ำอีกครั้งเมื่อผ่านไปครึ่งเวลา
  • ตั้ง timeout (shop_photo_confirm_timeout_min, ค่าเริ่ม 10 นาที)
  • ครบเวลาแล้วไม่ตอบ ให้ ถือว่ายืนยันอัตโนมัติ แล้วไปต่อ พร้อมบันทึกว่าเป็น auto-confirm (เผื่อมีข้อพิพาทภายหลัง)
  • ยอดยังถูกคุมด้วยวงเงินที่ลูกค้าตั้งไว้อยู่แล้ว auto-confirm จึงไม่ทำให้โดนเก็บเกินวงเงิน

ต้องให้ผู้ใช้ตัดสิน: auto-confirm เมื่อครบเวลา (คนขับไม่ต้องรอ แต่ลูกค้าอาจรู้สึกว่าถูกตัดสินใจแทน) หรือค้างไว้รอลูกค้าตลอด (ลูกค้าคุมเต็มที่ แต่คนขับติดอยู่กับงาน) — ดูหัวข้อ 8 Q5

4.4 ผลต่อฐานข้อมูล

  • shop_orders.proof_mode — 'receipt' | 'photo' (snapshot จาก issues_receipt ตอนสร้างออเดอร์ เพราะแอดมินอาจแก้ทีหลัง)
  • shop_orders.proof_urls — text[] รองรับหลายรูป
  • shop_orders.customer_confirmed_at, confirmed_by ('customer' | 'auto_timeout')
  • shop_orders.ai_extract — jsonb เก็บผลดิบจาก AI + usage + confidence

5Wallet เท่านั้น — เหตุผลด้านความปลอดภัย

ผู้ใช้สั่งให้ใช้ Wallet อย่างเดียว ซึ่งเป็นการตัดสินใจที่ถูกต้องสำหรับบริการประเภทนี้ ด้านล่างคือเหตุผลที่รองรับ เพื่อใช้อธิบายทั้งทีมงานและผู้ใช้ปลายทาง

1. คนขับไม่ต้องสำรองเงินตัวเอง

ถ้าเก็บเงินปลายทาง คนขับต้องควักเงินตัวเองจ่ายที่ร้านก่อน ถ้าลูกค้าไม่รับของ คนขับแบกของและหนี้นั้นไว้เอง — ของกินของสดคืนร้านไม่ได้ด้วย Wallet ย้ายความเสี่ยงนี้ออกจากคนขับทั้งหมด ซึ่งเป็นเงื่อนไขที่ทำให้หาคนขับมารับงานฝากซื้อได้จริง

2. ยืนยันความสามารถจ่ายก่อนเกิดต้นทุน

hold เกิดขึ้นก่อนคนขับออกเดินทาง ระบบจึงรู้แน่นอนว่าเงินมีอยู่จริง ไม่ใช่รู้ตอนคนขับถือของยืนอยู่หน้าบ้านลูกค้าแล้วพบว่าจ่ายไม่ได้ ต่างจากอาหารตรงที่ฝากซื้อมีมูลค่าสินค้าสูงกว่ามาก (หลักพัน ไม่ใช่หลักร้อย) ความเสียหายต่อเคสจึงสูงกว่า

3. ทุกบาทมีร่องรอยตรวจสอบได้

ทุกการเคลื่อนไหวลง wallet_transactions ทั้ง hold, settle, refund เวลามีข้อพิพาทว่า "จ่ายไปเท่าไหร่ คืนมาเท่าไหร่" มีหลักฐานครบ ขณะที่เงินสดไม่เหลือร่องรอยใด ๆ ในระบบเลย ต้องเชื่อคำบอกเล่าอย่างเดียว

4. คืนส่วนต่างได้อัตโนมัติ

ฝากซื้อเกือบทุกครั้งจ่ายจริงน้อยกว่าวงเงินที่กันไว้ ถ้าเป็นเงินสดคนขับต้องทอนเงินหน้าบ้าน ซึ่งผิดพลาดง่ายและเถียงกันได้ Wallet คืนส่วนต่างตรงเป๊ะทันทีที่ปิดงาน

5. ลดความเสี่ยงทางกายภาพของคนขับ

คนขับที่ต้องพกเงินสดหลักพันไปซื้อของตลอดวันตกเป็นเป้า ไม่ต้องถือเงินสดคือความปลอดภัยของตัวคนขับเอง

6. บังคับเพดานได้จริง

วงเงินที่ลูกค้าตั้งเป็นเพดานที่ระบบบังคับได้จริง เพราะเงินอยู่ในระบบ ถ้าเป็นเงินสดวงเงินเป็นแค่ตัวเลขแนะนำ ไม่มีอะไรหยุดการใช้จ่ายเกินได้

ราคาที่ต้องจ่ายสำหรับข้อดีเหล่านี้ (ต้องยอมรับให้ชัด)

  • ลูกค้าใหม่ที่ไม่มีเงินใน Wallet สั่งไม่ได้เลย เป็นอุปสรรคจริงและอาจเป็นตัวกั้นการเติบโตที่ใหญ่ที่สุดของฟีเจอร์นี้ ต้องทำทางเติมเงินให้ลื่นที่สุดในหน้า checkout (Q1 หัวข้อ 8)
  • เงินลูกค้าถูกกันไว้ระหว่างรอ ถ้าระบบมีบั๊กจน hold ค้าง ลูกค้าจะรู้สึกเหมือนเงินหาย — ต้องมี cron ปลด hold + แสดงใน Wallet ให้ชัดว่ากันไว้เพื่ออะไร
  • ระบบต้องแม่นเรื่องเงินทั้งหมด เพราะไม่มีเงินสดมารองรับตอนระบบพลาด

5.1 ผลต่อการทำงาน

  • payment_method ของ service_type 'shop' บังคับเป็น 'wallet' เท่านั้น — ตรวจที่ server ด้วย ไม่ใช่แค่ซ่อนตัวเลือกในแอป
  • หน้าเลือกวิธีจ่ายของฝากซื้อไม่ต้องมีตัวเลือก แสดงเป็นข้อความว่าใช้ Wallet พร้อมยอดคงเหลือ
  • แสดงยอดที่ถูกกันไว้ในหน้า Wallet แยกจากยอดใช้ได้ พร้อมลิงก์ไปออเดอร์ที่กันไว้

ต้องมีร้านในระบบก่อนถึงเปิดบริการได้ เริ่มกี่ร้าน พื้นที่ไหนก่อน และใครเดินสำรวจเวลาเปิด-ปิดจริง — เป็นงานคนไม่ใช่งานโค้ด แต่บล็อกการเปิดใช้งาน
