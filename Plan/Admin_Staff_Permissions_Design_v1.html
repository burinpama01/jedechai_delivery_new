ขอบเขตที่ตกลงแล้ว
  • superadmin แต่งตั้ง / ระงับผู้ช่วยแอดมินได้ · บัญชีแอดมินเดิม (1 บัญชี) = superadmin · มี superadmin ได้หลายคน แต่ระบบห้ามลดจนไม่เหลือ
  • การอนุมัติ ทั้งสองแบบ: ลำดับขั้น (superadmin › หัวหน้า › ผู้ช่วย) + งานสำคัญที่ผู้ช่วยทำได้แค่ "ส่งขออนุมัติ" ให้ขั้นสูงกว่ายืนยัน
  • สิทธิ์ 3 ชั้น: บทบาทสำเร็จรูป → ระดับรายหน้า (ไม่เห็น/ดู/แก้ไข/อนุมัติ) → ปรับราย action เป็นรายคน
  • ใช้ใน admin-web อย่างเดียว — หน้าจอแอดมินในแอปมือถือยังเป็นของ superadmin

2. หลักการออกแบบ

ปลอดภัยไว้ก่อน (deny by default)
ผู้ช่วยใช้ role ใหม่ staff — policy 73 จุด, verifyAdmin และหน้าแอดมินใน Flutter ไม่รู้จัก role นี้ จึงไม่ได้สิทธิ์อะไรเลยจนกว่าจะเปิดทีละหน้า
superadmin ไม่เปลี่ยน
role admin เดิมทำงานเหมือนเดิมทุกจุด (DB, edge function, admin-web, แอปมือถือ) — ไม่ต้องแก้ policy เดิม
เขียนข้อมูลผ่านประตูเดียว
staff เขียนได้ผ่าน admin-actions เท่านั้น (ตรวจสิทธิ์ + ส่งขออนุมัติ + บันทึก audit ที่จุดเดียว) — ไม่เปิดสิทธิ์เขียนตารางตรงให้ staff
ตรวจสิทธิ์ที่ server ทุกครั้ง
การซ่อนเมนู/ปุ่มใน UI เป็นแค่ความสะดวก สิทธิ์จริงตรวจใน DB (อ่าน) และ edge function (เขียน) ทุก request — ระงับบัญชีแล้วมีผลทันที

3. โมเดลสิทธิ์

3.1 ระดับในทีม (tier)

tierprofiles.roleทำอะไรได้
superadminadmin (เดิม)ทุกอย่าง · จัดการทีม/บทบาท/สิทธิ์ · อนุมัติทุกคำขอ · แต่งตั้ง superadmin เพิ่ม
หัวหน้า (lead)staffตามสิทธิ์ที่ได้ + อนุมัติคำขอของผู้ช่วย ในหน้าที่ตัวเองมีระดับ "อนุมัติ"
ผู้ช่วย (assistant)staffตามสิทธิ์ที่ได้ · งานสำคัญส่งขออนุมัติ

3.2 ระดับรายหน้า

ไม่เห็น ดู อ่านข้อมูลในหน้า แก้ไข ทำ action ทั่วไปในหน้า อนุมัติ ทำ action สำคัญได้เอง + อนุมัติคำขอของคนอื่นในหน้านั้น (ใช้ได้กับหัวหน้าขึ้นไป)

3.3 สามชั้นรวมกันอย่างไร

สิทธิ์จริงของ action X ในหน้า P สำหรับคน U
  1) ถ้า U มี override ราย action ของ X  → ใช้ค่านั้น (อนุญาต / ห้าม / ต้องขออนุมัติ)
  2) ไม่งั้นดูระดับหน้า P ของ U (override รายหน้า ทับ บทบาทสำเร็จรูป)
       action ทั่วไป : ต้องการ "แก้ไข"
       action สำคัญ  : "อนุมัติ" = ทำได้เลย · "แก้ไข" = ส่งขออนุมัติ · ต่ำกว่า = ห้าม
  3) superadmin ข้ามทุกขั้น

3.4 บทบาทสำเร็จรูปตั้งต้น (แก้/เพิ่มได้)

บทบาทหน้าหลัก (แก้ไข)ดูอย่างเดียว
ฝ่ายบัญชี/การเงินเติมเงิน, ถอนเงิน, กระเป๋าลูกค้า, รายได้ผู้ใช้, ออเดอร์
ฝ่ายดูแลร้านร้านค้า, เมนู, AI นำเข้าเมนู, ร้านฝากซื้อออเดอร์, รีวิว
ฝ่ายดูแลคนขับคนขับ, แผนที่ออเดอร์
ฝ่ายบริการลูกค้าร้องเรียน, ออเดอร์, ออเดอร์ค้าง, ออเดอร์ฝากซื้อ, ซักรีด, รีวิวผู้ใช้, คนขับ, ร้านค้า
ฝ่ายการตลาดโปรโมชัน, บรอดแคสต์, แนะนำเพื่อนแดชบอร์ด

หน้า ตั้งค่าระบบ, ทีมแอดมิน และ ลบบัญชีผู้ใช้ ตั้งต้นเป็นของ superadmin เท่านั้น (เปิดให้ทีละคนได้ด้วย override ยกเว้นทีมแอดมิน)

3.5 action สำคัญ (ตั้งต้น — ผู้ช่วยต้องขออนุมัติ)

5. การบังคับสิทธิ์

5.1 เขียน — ประตู admin-actions

  1. verifyAdminOrStaff(): role admin → superadmin · role staff + admin_staff.active → staff · อื่น ๆ 403
  2. หา action ในแคตตาล็อก → คำนวณสิทธิ์จริง (ข้อ 3.3) ทุก request ไม่ cache
  3. อนุญาต → ทำงาน + audit · ต้องขออนุมัติ → บันทึก admin_approval_requests (payload ที่ตรวจรูปแบบแล้ว) แจ้งผู้อนุมัติ ตอบ {pending_approval: id} · ห้าม → 403 + audit
  4. action ใหม่ decide_approval: ผู้อนุมัติ (superadmin หรือ lead ที่มีระดับอนุมัติในหน้านั้น) ≠ ผู้ขอ · ตรวจสิทธิ์ผู้อนุมัติ ณ เวลาอนุมัติ · ล็อกแถว (FOR UPDATE) กันอนุมัติซ้ำ · รัน payload เดิมในนามผู้อนุมัติ · เก็บผลลัพธ์
  5. RPC ที่ admin-web เรียก (เช่น admin_review_gp_proposal, shop_admin_set_trusted) และการเขียนตารางตรง (shop_stores, option_templates, merchant_ai_import_quota) → ย้ายมาผ่าน admin-actions หรือให้ RPC ตรวจสิทธิ์ staff เอง

5.2 อ่าน — RLS เพิ่ม policy SELECT สำหรับ staff

เพิ่ม policy FOR SELECT TO authenticated USING (staff_can_view('<page>')) บนตารางที่แต่ละหน้าใช้ (ทำตาราง map หน้า→ตารางระหว่างลงมือ) · ไม่แตะ policy เดิมของ superadmin · ตารางที่ staff ไม่ควรเห็นเลย: system_config_private, ตารางทีม/สิทธิ์ของคนอื่น, Vault

5.3 UI admin-web

  • ล็อกอิน: ยอม role admin หรือ staff ที่ active · โหลดสิทธิ์ตัวเองครั้งเดียวต่อหน้า
  • ซ่อนเมนูที่ "ไม่เห็น" · ปุ่มที่ต้องขออนุมัติขึ้นป้าย "ส่งขออนุมัติ" · ปุ่มที่ห้ามซ่อน
  • หน้าใหม่ ทีมแอดมิน (superadmin): เพิ่มสมาชิก, เลือก tier/บทบาท, ตารางสิทธิ์รายหน้า, override ราย action, ระงับ/เปิด, ประวัติการเปลี่ยนแปลง
  • หน้าใหม่ คำขออนุมัติ: คิวของผู้อนุมัติ (badge จำนวนรอ) · ผู้ขอเห็นสถานะ/เหตุผลตีกลับ · กรองตามหน้า/สถานะ
  • หน้า บันทึกการทำงาน (audit) สำหรับ superadmin

6. กฎความปลอดภัย

  • ต้องเหลือ superadmin ที่ใช้งานได้อย่างน้อย 1 คนเสมอ (ตรวจใน DB)
  • เฉพาะ superadmin จัดการทีม/บทบาท/สิทธิ์ · staff แก้สิทธิ์ตัวเองไม่ได้ · ห้ามอนุมัติคำขอของตัวเอง
  • คำขอหมดอายุ 48 ชม. · payload ถูกตรวจและแช่แข็งตอนส่ง ผู้อนุมัติเห็นสรุปที่อ่านง่ายก่อนกด
  • ทุก action ของ staff และทุกการเปลี่ยนสิทธิ์ บันทึก audit (ไม่เก็บข้อมูลลับใน summary)
  • เปลี่ยน role ผู้ใช้เป็น staff/admin ได้ผ่าน admin-actions ของ superadmin เท่านั้น (ตรวจว่า trigger กันยกระดับ role ใน profiles ยังครอบคลุม role ใหม่)

7. แบ่งเฟส

เฟสเนื้อหาผลที่ได้
P1 ฐานrole staff + ตารางใหม่ + ฟังก์ชันสิทธิ์ + แคตตาล็อก action · ประตู admin-actions (อนุญาต/ห้าม/ขออนุมัติ) + decide_approval + audit · หน้า ทีมแอดมิน / คำขออนุมัติ · ล็อกอิน staff + ซ่อนเมนู/ปุ่มสร้างทีมและสิทธิ์ได้ แต่ staff ยังเห็นได้แค่หน้าที่ทำ policy อ่านแล้ว
P2 หน้าหลักpolicy อ่าน + ย้าย RPC/เขียนตรง สำหรับ: ออเดอร์, ออเดอร์ค้าง, คนขับ, ร้านค้า, ผู้ใช้, เติมเงิน, ถอนเงิน, ร้องเรียนบทบาทบัญชี / ดูแลร้าน / ดูแลคนขับ / บริการลูกค้า ใช้งานได้จริง
P3 หน้าที่เหลือเมนู, AI นำเข้าเมนู, ฝากซื้อ, ซักรีด, โปรโมชัน, บรอดแคสต์, แนะนำเพื่อน, รีวิว, รายได้, แผนที่, แดชบอร์ด, ลบบัญชี, แจ้งเตือนครบ 24 หน้า

แต่ละเฟส: migration ทดสอบใน PostgreSQL แยก + BEGIN/ROLLBACK บน prod ก่อน apply · test สิทธิ์ (superadmin/lead/assistant/ระงับ/ไม่ใช่ทีม) ทุก action ที่เปิด · code_reviewer · deploy edge function ก่อน migration ที่ต้องพึ่ง

8. ความเสี่ยงและข้อจำกัด

  • admin-actions ใน working tree มีงาน GP Proposal ที่ยังไม่ขึ้น production — ต้อง merge/deploy งาน GP ก่อน หรือแยก branch ให้ชัด ก่อนแก้ประตูสิทธิ์ (ไม่อย่างนั้น deploy แล้วงาน GP จะหลุดขึ้นไปด้วย)
  • staff ที่มีสิทธิ์ "ดู" จะเห็นข้อมูลส่วนตัวลูกค้า/คนขับตามหน้า — เป็นไปตามที่ superadmin ตั้ง แต่ควรมี audit การเปิดดูหน้า (P3 ถ้าต้องการ)
  • การ map หน้า→ตาราง อาจตกหล่น ทำให้หน้าบางส่วนว่างสำหรับ staff (ไม่รั่ว แค่ใช้ไม่ได้) — ทดสอบด้วยบัญชี staff จริงทุกหน้า
  • หน้าแอดมินในแอปมือถือไม่ครอบคลุม (ตามขอบเขต) — staff ล็อกอินแอปจะเห็นหน้าลูกค้า

9. คำถามที่ต้องตัดสินใจก่อนเริ่ม P1

  1. สร้างบัญชีผู้ช่วยอย่างไร — (ก) แปลงบัญชีที่สมัครแล้วด้วยอีเมล (ข) superadmin สร้างบัญชีใหม่ + ส่งลิงก์ตั้งรหัสผ่าน (ค) ได้ทั้งสองแบบ
  2. หัวหน้าอนุมัติได้แค่หน้าที่ตัวเองมีระดับ "อนุมัติ" หรือให้อนุมัติได้ทุกคำขอของผู้ช่วยในทีม
  3. แจ้งผู้อนุมัติเมื่อมีคำขอใหม่ — ใช้คิว Telegram/LINE เดิม (notify-admin-events) ด้วยไหม
  4. บทบาทสำเร็จรูปตั้งต้น 5 บทบาทในข้อ 3.4 / รายการ action สำคัญในข้อ 3.5 ใช้ได้ไหม
  5. งาน GP Proposal ใน working tree — ให้ commit/deploy ให้จบก่อนเริ่มงานนี้ไหม
