3) การออกแบบเชิงเทคนิค

A. ชดเชยส่วนลดตอน complete (แกนหลัก) — แก้ใน complete_booking ฝั่ง DB

  • ที่ไหน: ใน public.complete_booking หลังหัก commission สำเร็จ ก่อน UPDATE status (ธุรกรรมเดียวกัน — สำเร็จครบหรือ rollback ทั้งหมด)
  • เงื่อนไข: service_type='food' + มีแถวใน coupon_usages ของ booking นี้ + discount_amount > 0 + เฉพาะเงินสด/โอน (payment_method IN ('cash','transfer')) — เหตุผล: คนขับแบกส่วนลดเฉพาะออเดอร์ที่ตัวเองเก็บเงินสด (ออเดอร์จ่าย Wallet ฝั่งคนขับไม่ได้เก็บเงิน — ดูข้อ 5 คำถามเปิด)
  • กลไก: เรียก wallet_topup(p_driver_id, v_discount, 'ชดเชยส่วนลดคูปอง ออเดอร์ FD-…', 'coupon_compensation', p_booking_id) — RPC มีอยู่แล้ว รองรับ type + related_booking_id
  • Idempotency (กันเติมซ้ำ): เช็คก่อนว่าไม่มี ledger type='coupon_compensation' AND related_booking_id= ตัวนี้อยู่แล้ว + ตัว status-guard เดิมของ complete_booking กัน double-complete อยู่แล้ว (เรียกซ้ำหลัง completed จะโดน invalid_status)
  • แจ้งเตือน: INSERT ลง notifications ถึงคนขับ ตามแพทเทิร์นเดิม (FCM วิ่งตามระบบแจ้งเตือนปัจจุบัน):
    • type: driver.coupon_compensated
    • หัว: "💵 ชดเชยส่วนลดคูปอง"
    • เนื้อ: "ระบบเติมเงินชดเชยส่วนลด ฿{amount} สำหรับออเดอร์ {FD-XXXXXXXX} เข้ากระเป๋าของคุณแล้ว"
    • data: {booking_id, coupon_code, amount} + screen โหมด wallet/รายได้
  • ผู้ใช้เห็นตรงไหน: กระเป๋าคนขับ (wallet screen) มีรายการ "ชดเชยส่วนลดคูปอง" + แจ้งเตือน + (option) แถวในหน้ารายได้รายวัน

B. คืนคูปองเมื่อยกเลิก (C2) — แก้ใน cancel_wallet_booking_with_refund + admin_force_cancel_booking_with_wallet_refund

  • เมื่อยกเลิก booking ที่มี coupon_usages: ลบแถว usage + used_count = used_count − 1 (ไม่ต่ำกว่า 0) + ถ้ามี user_coupons.used_booking_id = bookingนี้ → คืน status='claimed', เคลียร์ used_booking_id/used_at
  • เหตุผลที่ "ลบ" ไม่ใช่ " flag": การนับ per_user_limit นับจากจำนวนแถว — ต้องลบจริงถึงจะคืนสิทธิ์ (ยอมรับว่าประวัติ "เคยใช้แล้วถูกยกเลิก" หาย — ดูได้จาก booking อยู่แล้ว)
  • หมายเหตุประสานงาน: แผนรวม Phase 2 (F2) จะแก้ฟังก์ชันเดียวกัน (เพิ่ม status_origin) — ถ้าทำพร้อมกันให้รวม migration เดียว ถ้าทำก่อนก็ไม่ชนกัน (คนละส่วนของ body)

C. ย้ายการคำนวณส่วนลดขึ้น server (C3) — แก้ apply_coupon_atomic

  • เพิ่มพารามิเตอร์: p_order_subtotal numeric, p_delivery_fee numeric, p_service_type text, p_merchant_id uuid (signa เดิมคงไว้ไม่ได้เพราะมี parameter ใหม่ — ทำ DROP+CREATE แบบเดียวกับที่เคยทำกับ mark_food_ready_guarded แล้วแอปเรียกใหม่)
  • Server ตรวจเพิ่ม (ทุกข้อมาจาก booking จริงหรือที่ client ส่งแล้ว server เทียบกับ bookings row): service_type ตรง, merchant_id ตรง (ถ้าคูปองระบุร้าน), min_order ผ่าน, แล้วคำนวณ discount เองตามสูตรเดียวกับ Coupon.calculateDiscount: base = discount_base('delivery_fee') ? delivery_fee : subtotal → percentage (เพดาน max) / fixed (ไม่เกิน base) / free_delivery (= delivery_fee)
  • บันทึก discount ที่ server คำนวณเท่านั้น — p_discount_amount จาก client ไม่ใช้แล้ว (แอปเดิมยังส่งมา → RPC ใหม่รับ signature เดิมแบบ optional ได้หรือแอปต้องอัปเดตพร้อมกัน — เลือก: deploy RPC ที่รับ parameter ใหม่ทั้งหมด + แอปอัปเดตพร้อม release เพราะ checkout เป็นจุดเดียวที่เรียก)
  • แอปเก่าช่วงเปลี่ยนผ่าน: ยังเรียก signature เก่าได้ → ให้ RPC คำนวณจาก booking row โดยตรงแทน (อ่าน price/delivery_fee จาก bookings — ไม่ต้องรับจาก client เลย) — ตัดสินใจ design: อ่านจาก bookings ทั้งหมด = ไม่ต้องเพิ่ม parameter ไม่ต้องเปลี่ยนแอป ✓ (แนะนำ)

D. แก timezone (C4)

  • getClaimableCoupons/getAvailableCoupons: เลิกใช้ _bangkokNowIso() — เปลี่ยนเป็นกรองด้วย RPC เล็ก (list_active_coupons ใช้ now()) หรือส่ง timestamp แบบมี offset (UTC ISO) ให้ตรง semantics ของ timestamptz
  • ตรวจจุดเขียนวันที่ตอนสร้างคูปอง (แอดมิน/ร้าน) ให้ส่ง UTC เสมอ — คูปองเดิม 7 ใบมีค่าที่เขียนแบบ naive อยู่แล้ว → script ปรับ data ครั้งเดียว +7 ชม. ให้เป็น UTC จริง (จำนวนน้อย ตรวจทีละใบก่อน-หลัง)

5) คำถามเปิด / จุดต้องยืนยันระหว่าง implement

สำคัญที่สุด — ออเดอร์ "จ่ายผ่าน Wallet" คนขับได้เงินยังไง: จากการอ่าน complete_booking ระบบมีแค่ "หัก commission จากกระเป๋าคนขับ" ไม่เห็นการเครดิตค่าจ้างคนขับสำหรับออเดอร์ที่ลูกค้าจ่าย wallet → ต้อง verify ก่อน implement ว่า wallet orders เครดิตคนขับตรงไหน ถ้าคนขับ wallet-order ได้เต็มจากระบบอยู่แล้ว → ไม่ต้องชดเชยใบนั้น (เงื่อนไข A ครอบคลุมแล้วด้วย cash/transfer-only) · ถ้ายังไม่มีใครเครดิต → เป็นหนี้เทคนิคที่ต้องแยกงาน (ไม่ขยาย scope แผนนี้)
ยืนยันเบื้องต้นระหว่าง implement (เช็ค 5 นาที): (1) booking เงินสดที่ complete แล้วทุกออเดอร์หัก commission จากกระเป๋าจริง (ledger 41 รายการยืนยันแนวนี้) (2) wallet_topup ใช้จาก SECURITY DEFINER ได้ (laundry_payout เคยใช้ pattern นี้แล้ว ✓) (3) การแจ้งเตือนใช้ trigger เดิมของ notifications → FCM อัตโนมัติ

6) แผนทดสอบ (TDD)

  • Unit/smoke (เขียนก่อน — red): migration มี wallet_topup('coupon_compensation') + notifications insert + cancel แก้ coupon_usages + apply_coupon_atomic คำนวณเอง (assert ไม่รับ p_discount_amount เป็นความจริงอีก)
  • E2E rollback (แพทเทิร์น 19 ก.ย.): ใน transaction ที่ rollback:
    1. สร้าง booking เงินสด + coupon_usages จำลอง → เรียก complete_booking → ต้องเห็น ledger +25 type=coupon_compensation + notifications 1 แถว + wallet balance คนขับบวกขึ้น 25
    2. เรียก complete ซ้ำ → invalid_status (ไม่เติมซ้ำ)
    3. ยกเลิกออเดอร์ที่มีคูปอง → coupon_usages หาย + used_count ลด + user_coupons คืน claimed
    4. apply_coupon_atomic กับคูปอง percentage → discount ที่บันทึก = ผลคำนวณ server (ไม่ใช่ค่าที่ client อ้าง)
  • ทดสอบจริงบน emulator หลัง deploy: สั่งอาหารด้วยคูปองทดสอบ (สร้าง NEWUSER02) → คนขับจบงาน → เช็คกระเป๋า + แจ้งเตือน + ยอดรวมวัน = ค่าจ้างเต็ม
  • Regression: ชุด node smoke เดิม + flutter analyze scoped + ห้ามมี fail ใหม่

7) Rollback

  • ทุกฟังก์ชันเป็น CREATE OR REPLACE → เก็บ def เดิมไว้ใน comment ของ migration แล้ว reverse ด้วยการ CREATE OR REPLACE กลับ
  • ledger/notifications ที่เกิดแล้วไม่ต้องลบ (เงินจริงเข้ากระเป๋า — ย้อนด้วย admin_adjustment เป็นรายกรณี)
  • สคริปต์ปรับวันที่คูปอง (+7 ชม.): เก็บค่าเดิมในตาราง backup ชั่วคราวก่อนรัน
ผลลัพธ์ที่คาดหวังเมื่อจบแผน: คนขับไม่ขาดเงินจากคูปองอีก (มีหลักฐาน ledger + แจ้งเตือนทุกครั้ง) · ลูกค้าที่ยกเลิกได้คูปองคืน · จำนวนส่วนลดฝั่ง server คำนวณเดียว · รายการคูปองไม่เพี้ยน 7 ชม.
สถานะ: Planning — รออนุมัติ · ประเมิน: DB 4 ขั้น (รวมเป็น 1–2 ไฟล์ migration) + แอปเล็กน้อย (label) + tests · ทำต่อเนื่องจบใน 1 session ได้ · เชื่อมกับแผนรวม: ข้อ A ใช้จุดเดียวกับ G2 (complete_booking) — ถ้าทำแผนรวม Phase 2 พร้อมกันให้รวม migration
