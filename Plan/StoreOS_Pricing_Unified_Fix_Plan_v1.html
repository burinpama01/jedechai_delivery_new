2) แผนตาม Phase

Phase 1 — ราคาทุกจอตรงกัน (P1, P2) · งานเล็ก เห็นผลทันที · ไม่ต้องมี migration

รถที่ไปถึงมือผู้ใช้: release ถัดไป (bump version ตามกฎ repo)

  • สร้าง helper เดียว: เพิ่ม RoleAmountCalculator.ceilBaht(double) (+ optional formatBaht() แสดงทศนิยมเมื่อ < จำนวนเต็ม) ให้เป็นจุดปัดเงินเดียวของทั้งแอป
  • ฝั่งลูกค้า: customer_order_detail_screen, activity_screen เปลี่ยน .ceil() ตรงๆ → helper (ไม่เปลี่ยนพฤติกรรมปัจจุบัน แค่รวมจุด)
  • ฝั่งคนขับ: driver_dashboard_screen เปลี่ยน toStringAsFixed(0) ของเงินทั้งหมด (ยอดเก็บ/ค่าอาหาร/ค่าส่ง/ค่าจ้าง) → helper — จุดที่ทำให้เห็นต่างกัน 1 บาท
  • ฝั่งร้าน: ตรวจ merchant order_detail/orders ใช้ helper เดียวกัน
  • กันถอยหลัง: smoke test ห้ามพบ toStringAsFixed(0) กับตัวแปรเงินบนหน้า order ของ 3 ฝั่ง + unit test helper
  • Verify: unit test + smoke + scoped analyze + ทดสอบมือบน emulator (ออเดอร์ค่าส่งทศนิยม เช่น 5.49) เทียบ 3 จอต้องเห็นยอดเดียวกัน

Phase 2 — เงินปลอดภัย + สถานะถึง POS ครบ (F2, G2) · มี migration · deploy server ก่อน app

ระดับ: สูงสุดของแผน — ทั้งสองข้อมีหลักฐานเกิดจริงแล้ว

  • M2.1 (F2): migration ใหม่ CREATE OR REPLACE cancel_wallet_booking_with_refund + admin_force_cancel_booking_with_wallet_refund — เพิ่ม status_origin = 'jdc' ใน UPDATE สถานะ (ดึง body ปัจจุบันจาก DB มาแก้ ห้ามเขียนใหม่จากความจำ)
    • ผล: ทุกการยกเลิกจาก JDC บอก POS เสมอ แม้ status ล่าสุดมาจาก POS
  • M2.2 (G2): migration แก้ complete_booking — คำนวณ app_earnings/driver_earnings จาก connect_merchant_gp_amount (มีอยู่แล้ว, สูตรเดียวกับ webhook) แบบ authoritative; ค่าที่ client ส่งมาเก็บไว้เทียบ (เช่น details->>'client_claimed_earnings') กรณีต่างกัน log ใน notes/audit — ไม่ห้าม transaction เสร็จงานแต่เงินใช้เลข server
  • Deploy order: M2.1 → M2.2 → แล้วค่อย release แอป (แอปเก่ายังส่ง p_earnings มา — RPC ใหม่รองรับ/ignore ได้ จึงไม่ break แอปเดิม)
  • Verify: E2E rollback simulation แบบที่ใช้วันนี้ — (ก) cancel ออเดอร์ origin='storeos' แล้วเช็ค webhook order.status ถูกคิว (pg_net) (ข) complete ออเดอร์จริงใน txn แล้วเทียบ earnings server vs client ต้องตรงสูตร + smoke tests
  • Rollback: เก็บ function defs เดิมไว้ใน comment migration / สามารถ CREATE OR REPLACE กลับ

Phase 3 — ข้อมูลครบ ตรวจสอบย้อนหลังได้ (G1, G4, P3) · มี migration + backfill เลือกได้

  • M3.1 (G1): เพิ่มคอลัมน์ snapshot บน bookings: gp_system_rate_at_order, gp_driver_rate_at_order + trigger BEFORE INSERT (food) กรอกจาก profiles อัตโนมัติ — immunity ต่อแอปเวอร์ชันเก่าเพราะทำที่ DB
    • พร้อม audit: trigger บน profiles เมื่อแก้ 3 คอลัมน์ GP → บันทึกลง gp_rate_audit (เก่า/ใหม่/ใคร/เมื่อไร)
  • M3.2 (G4): complete_booking (จาก Phase 2) เติม total_amount = price + delivery_fee − coupon, platform_gp_amount, merchant_net_amount ให้ food เหมือน laundry + script backfill ออเดอร์เก่า (optional ทำเฉพาะ completed)
  • M3.3 (P3): trigger StoreOS outbound เพิ่ม field coupon_discount + net_total (อ่านจาก coupon_usages ตอนสร้าง event) — ประสานกับฝั่ง StoreOS รับ field ใหม่ (ไม่ breaking — เพิ่ม field)
  • Verify: สั่งออเดอร์ทดสอบ → เช็ค snapshot ถูกกรอก แม้สั่งจากแอปเก่า / เปลี่ยน rate ร้านกลางทาง → complete แล้วตัวเงินใช้ rate ณ วันสั่ง ตามนโยบายที่เลือก (ดูหมายเหตุ)
การตัดสินใจที่ต้องมีเจ้าของ (ก่อน implement M3.1): ตอน complete จะใช้ rate ณ วันสั่ง (แนะนำ — ล็อกตามที่คุยตอนสั่ง) หรือ ณ วันจบ (สถานะปัจจุบัน)? — แนะนำวันสั่ง แล้ว snapshot คอลัมน์ใหม่จะเป็น source ของ complete_booking ใน Phase 2

Phase 4 — นโยบายธุรกิจ + ความทนทาน (G3, F4, F5, F8) · แยกย่อยตามความพร้อม

  • G3 (ก่อนเปิดคูปองระบบจริง): ตัดสินใจ "ใครแบกส่วนลด" — ตัวเลือก: (ก) หักจาก GP ระบบ (แนะนำ — platform เป็นคนออกคูปอง) (ข) ชดเชยกระเป๋าคนขับอัตโนมัติตอน complete (ค) ร้านแบก (ใช้ path applyMerchantCreatedDiscount เดิม) → implement ใน M2.2/M3.2 พร้อม test สถานการณ์เงินสด+คูปอง
  • F4: ตาราง pos_outbound_events (event_id, topic, booking_id, queued_at, สถานะจาก pg_net) + หน้า admin ดู "event ล่าสุดไป StoreOS" — ไม่ทำ retry engine ในรอบนี้ แค่มองเห็น
  • F5: เพิ่มตาราง mapping ร้าน JDC ↔ StoreOS + trigger outbound push เฉพาะร้านลงทะเบียน — ทำเมื่อมีร้านเข้าใช้จริง > 1–2 ร้าน
  • F8: เพิ่ม field shop_status_source + แสดง toast ในแอป merchant เมื่อ POS เปลี่ยนสถานะ (optional)
  • F3 (รับออเดอร์ทาง POS): เป็น feature ใหม่ — ทำแผนแยกเมื่อธุรกิจยืนยัน need

  • ทุก migration: สมมติฐานทดสอบแบบ E2E rollback transaction (แพทเทิร์นเดียวกับที่ใช้ 19 ก.ย. — จริง ปลอดภัย ไม่แต้มข้อมูล) + supabase migration repair + ยืนยัน marker บน remote
  • ทุกงาน: TDD — เขียน smoke/unit test ก่อน (red) → implement → green → scoped analyze → รวม suite เดิมต้องไม่มี fail ใหม่
