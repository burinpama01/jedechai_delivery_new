ระบบฝากซื้อ / ฝากหิ้ว
(Shop & Errand Service)

บริการใหม่ที่ลูกค้าพิมพ์รายการของที่อยากได้เอง เลือกร้านของชำ/ห้าง แล้วให้คนขับไปซื้อและส่งให้ โดยกันวงเงินจาก Wallet ล่วงหน้า แล้วกระทบยอดตามใบเสร็จจริง

service_type = shop รายการแบบพิมพ์เอง (free-text) Pre-auth Wallet ค่าบริการตั้งค่าได้ใน Admin Phase 1: Customer + Driver + Admin ฐาน: app 1.14.0+125

1สรุปผู้บริหาร

ฝากซื้อไม่ใช่ food delivery ที่ไม่มีเมนู ความต่างที่แท้จริงคือ ราคาไม่ทราบจนกว่าคนขับจะจ่ายเงินที่ร้าน ทั้งโครงสร้างข้อมูล เงิน และ UX จึงต้องออกแบบรอบ "ความไม่แน่นอนของราคา"

ปัญหาหลัก

  • ของอาจหมด / ราคาต่างจากที่คิด
  • ต้องมีวงเงินกันไว้ ไม่งั้นคนขับเสี่ยงสำรองแล้วลูกค้าไม่รับ
  • ต้องมีหลักฐาน (ใบเสร็จ) ก่อนตัดเงินจริง

ทางออกที่เลือก

  • ลูกค้าตั้ง วงเงินสูงสุด ตอนสั่ง แล้วระบบ hold จาก Wallet
  • คนขับซื้อจริง กรอกยอด + ถ่ายใบเสร็จ
  • ระบบกระทบยอด เก็บเท่าที่จ่ายจริง + ค่าบริการ คืนส่วนต่างเข้า Wallet

สิ่งที่นำของเดิมมาใช้

  • ตาราง bookings + matching คนขับ
  • รูปแบบ hold จาก laundry (wallet_transactions.type='hold')
  • โครง settlement ฝั่ง server จาก Batch 1
  • Storage สำหรับรูป (ใช้เดียวกับรูปพัสดุ)

2ขอบเขตที่ผู้ใช้ยืนยัน

หัวข้อตัดสินใจผลต่อการออกแบบ
รูปแบบรายการพิมพ์เองอย่างเดียว (free-text)ไม่ต้องทำ merchant catalog / onboarding ร้าน — ร้านเป็นแค่จุดหมาย (ชื่อ + พิกัด)
เงินค่าสินค้ากันวงเงินจาก Wallet ก่อน (pre-auth)คนขับไม่ต้องสำรองเอง แต่ลูกค้าต้องมียอดใน Wallet ก่อนสั่ง จึงต้องมีทางลัดเติมเงินในหน้า checkout
ค่าบริการค่าส่งตามระยะ + % ของบิล + ขั้นบันได โดย Admin ตั้งค่าได้ทั้งหมดต้องทำ fee engine แบบ config-driven ใน system_config ไม่ hard-code ในแอป
Phase 1Customer + Driver + Admin webไม่ทำฝั่ง Merchant — ร้านไม่เห็นออเดอร์ (ยกไป Phase 2 ถ้าต้องการ)
ข้อสังเกตที่ต้องตัดสินใจก่อนลงมือ (ดูหัวข้อ 9): วงเงิน pre-auth หมายถึงลูกค้าต้องมีเงินใน Wallet เต็มจำนวนก่อนสั่ง ซึ่งอาจกั้นผู้ใช้ใหม่จำนวนมาก แผนนี้จึงเสนอทางลัดเติมเงินและ fallback ไว้ให้พิจารณา

3Flow หลัก

3.1 เส้นทางปกติ (Happy path)

ลูกค้าพิมพ์รายการ→ เลือกร้าน + ที่ส่ง→ ตั้งวงเงินสูงสุด→ ระบบ hold Wallet→ คนขับรับงาน→ ถึงร้าน / ซื้อของ→ กรอกยอดจริง + ถ่ายบิล→ ส่งของ→ settle + คืนส่วนต่าง

3.2 สถานะ (status machine)

สถานะความหมายใครเปลี่ยน
pendingสร้างแล้ว hold เงินแล้ว กำลังหาคนขับระบบ
acceptedคนขับรับงานคนขับ
shopping ใหม่คนขับถึงร้าน กำลังเลือกของคนขับ
awaiting_confirm ใหม่มีของไม่ครบ/ราคาเกินวงเงิน รอลูกค้ายืนยันระบบ (จาก checklist คนขับ)
purchased ใหม่ซื้อครบ กรอกยอดจริง + ใบเสร็จแล้วคนขับ
deliveringกำลังนำส่งคนขับ
completedส่งถึง + settle เงินเรียบร้อยคนขับ แล้ว server settle
cancelledยกเลิก แล้วคืน hold ตามนโยบายหัวข้อ 6.3ลูกค้า/คนขับ/แอดมิน

3.3 เส้นทางแตก (ที่ต้องออกแบบให้ดี)

ของไม่มี / ของหมด

คนขับติ๊ก "ไม่มีของ" รายตัว ระบบส่งแจ้งเตือนหาลูกค้าพร้อมตัวเลือก: ข้ามรายการนี้ / ให้คนขับเลือกของแทน / ยกเลิกทั้งออเดอร์ ถ้าลูกค้าไม่ตอบใน N นาที (config) ให้ถือว่า "ข้ามรายการนี้"

ราคาเกินวงเงิน

คนขับกรอกยอดแล้วเกิน hold ออเดอร์เข้า awaiting_confirm ลูกค้าต้องกดเพิ่มวงเงิน (hold เพิ่ม) ถึงจะไปต่อได้ ถ้า Wallet ไม่พอ ให้เติมเงินหรือลดของ

ลูกค้าไม่รับของ

ของซื้อแล้วคืนร้านไม่ได้ นโยบาย: ยังคิดเต็มจำนวน (ค่าสินค้า + ค่าบริการ) และให้แอดมินเป็นผู้ตัดสินกรณีพิพาทผ่านหน้า Admin

ยกเลิกหลังคนขับซื้อแล้ว

ปุ่มยกเลิกฝั่งลูกค้าต้องถูกปิดทันทีที่สถานะถึง purchased และต้องบังคับที่ฝั่ง server ด้วย ไม่ใช่แค่ซ่อนปุ่ม

4โครงสร้างฐานข้อมูล

ใช้ bookings เป็นแกนเหมือน vertical อื่น แล้วแยกรายละเอียดเฉพาะฝากซื้อออกเป็น 2 ตารางใหม่ (ตามแบบ parcel_details)

4.1 ตารางใหม่

ตารางคอลัมน์สำคัญหมายเหตุ
shop_orders ใหม่ booking_id (FK, unique), store_name, store_address, store_lat/lng, budget_cap, actual_goods_amount, service_fee, delivery_fee, total_amount, receipt_url, hold_transaction_id, refund_transaction_id, fee_config_snapshot (jsonb), substitution_policy, customer_note ทุกยอดเงินเป็น numeric(12,2) ห้ามใช้ double (บทเรียนจาก bookings.price)
shop_order_items ใหม่ shop_order_id, line_no, name_text, quantity_text, note, status (pending|bought|unavailable|substituted), actual_price, substitute_name quantity_text เป็น text เพราะลูกค้าพิมพ์ "2 ขวด" หรือ "ครึ่งโล" ไม่ใช่ตัวเลขเสมอ

4.2 แก้ของเดิม

  • bookings.service_type — รองรับค่า 'shop' (เป็น text อยู่แล้ว ต้องไล่แก้จุดที่ hard-code list 'ride','food','parcel')
  • coupons.service_type — เพิ่ม 'shop' ให้คูปองใช้กับฝากซื้อได้
  • system_config — เพิ่ม key กลุ่ม shop_* (หัวข้อ 5)
  • Realtime publication — เพิ่ม shop_orders, shop_order_items เพื่อให้ลูกค้าเห็นคนขับติ๊กของแบบสด

4.3 RLS (ตามบทเรียน Batch 0)

  • ลูกค้า: SELECT เฉพาะออเดอร์ตัวเอง · INSERT ผ่าน RPC เท่านั้น · ห้าม UPDATE คอลัมน์เงินทุกตัว
  • คนขับ: SELECT เฉพาะออเดอร์ที่ตัวเองถูก assign (หรือ pending ในรัศมี) · UPDATE ได้เฉพาะ status, ข้อมูล item, receipt_url
  • ยอดเงินทุกตัวคำนวณโดย ฟังก์ชันฝั่ง server เท่านั้น client ส่งได้แค่ "ราคาต่อรายการที่อ่านจากบิล" ซึ่งต้องผ่าน validation
  • ตั้ง SECURITY DEFINER + SET search_path = public ทุก RPC (บทเรียน HMAC trigger)

5Fee Engine (ตั้งค่าได้ใน Admin)

ผู้ใช้เลือก "ทั้ง 3 แบบ + admin ตั้งได้" จึงออกแบบเป็นสูตรเดียวที่ปิด/เปิดแต่ละส่วนได้

ค่าบริการรวม = ค่าส่งตามระยะ
              + max( ค่าฝากซื้อขั้นบันได , ค่าฝากซื้อแบบ % ของบิล )
              [+ ค่าบริการเพิ่มเติมต่อรายการ ถ้าเปิด]
Config keyตัวอย่างค่าความหมาย
shop_enabledfalseสวิตช์เปิดบริการ — ปล่อยเป็น false ตอน deploy เปิดเมื่อพร้อม
shop_delivery_fee_mode"reuse_ride"ใช้สูตรค่าส่งเดิมของ ride/parcel หรือตั้งแยก
shop_fee_percent10% ของยอดบิลจริง
shop_fee_tiers[{max:500,fee:30},{max:1500,fee:50},{max:null,fee:80}]ขั้นบันไดตามยอดบิล
shop_fee_min / shop_fee_max25 / 200เพดานล่าง-บน กันค่าบริการพุ่งเวลาบิลใหญ่
shop_budget_buffer_percent15ระบบแนะนำวงเงิน = ประมาณการ + buffer
shop_max_items / shop_max_budget30 / 5000กันสั่งเกินตัว / กันคนขับแบกของเยอะเกิน
shop_driver_share_percent80ส่วนแบ่งค่าบริการที่เข้าคนขับ
shop_substitution_timeout_min5ลูกค้าไม่ตอบเรื่องของหมดภายในกี่นาที
กฎสำคัญ: ตอนสร้างออเดอร์ต้อง snapshot config ลง fee_config_snapshot แล้วคิดเงินจาก snapshot เสมอ (ตรงกับ G1 ของ Batch 1) ไม่งั้นแอดมินแก้ค่าระหว่างวันแล้วออเดอร์เก่าคิดเงินเปลี่ยน

6กลไกเงิน (หัวใจของฟีเจอร์)

6.1 Pre-auth (ตอนสร้างออเดอร์)

ทำตามแบบที่ laundry ใช้อยู่แล้ว คือหักยอดออกจาก wallets.balance จริง แล้วบันทึก wallet_transactions type 'hold'

hold_amount = budget_cap + ค่าบริการประมาณการ (จาก fee snapshot ที่ budget_cap)

ถ้า balance < hold_amount  =>  ปฏิเสธ + คืน error 'insufficient_balance'
                                พร้อมส่ง required / balance กลับไปให้ UI เสนอเติมเงิน

6.2 Settlement (ตอนจบงาน)

ค่าสินค้าจริง   = SUM(shop_order_items.actual_price ที่ status='bought'|'substituted')
ค่าบริการ       = คำนวณจาก fee_config_snapshot โดยใช้ "ค่าสินค้าจริง"
ยอดที่เก็บจริง  = ค่าสินค้าจริง + ค่าบริการ + ค่าส่ง - ส่วนลดคูปอง
ส่วนต่างคืน     = hold_amount - ยอดที่เก็บจริง        => คืนเข้า Wallet (type 'refund')
คนขับได้รับ     = ค่าสินค้าจริง (คืนเงินที่สำรอง) + ส่วนแบ่งค่าบริการ + ค่าส่ง
ทั้งหมดนี้อยู่ใน RPC เดียว complete_shop_booking() ที่ทำงานเป็น transaction เดียว ถ้า settle ล้มเหลว ห้ามปล่อยให้ status เป็น completed

6.3 นโยบายยกเลิก

ยกเลิกตอนสถานะคืนเงินเหตุผล
pending, acceptedคืนเต็ม 100%ยังไม่มีต้นทุนเกิดขึ้น
shoppingคืนค่าสินค้าเต็ม หักค่าเสียเวลาคนขับ (config)คนขับเดินทางไปแล้ว
purchased ขึ้นไปยกเลิกไม่ได้ของซื้อแล้ว คืนร้านไม่ได้ ต้องผ่านแอดมินเท่านั้น

6.4 ความเสี่ยงที่ต้องปิดให้ได้

  • คนขับกรอกยอดเกินจริง — บังคับแนบรูปใบเสร็จก่อนเปลี่ยนเป็น purchased + ตั้ง threshold ให้ยอดที่ต่างจากประมาณการเกิน X% เข้าคิวให้แอดมินตรวจ
  • hold ค้าง (orphan hold) — ต้องมี pg_cron ปลดล็อก hold ของออเดอร์ที่ค้าง pending เกิน N ชั่วโมง บทเรียน: cron auto-shop-schedule เคยตายเงียบเพราะ GUC หาย ต้องมี health check
  • double settle — ใส่ guard ว่า completed_at IS NULL และ lock แถวด้วย FOR UPDATE
  • ปัดเศษ — ใช้กฎปัดเศษกลางเดียวกับ Batch 2 ห้ามปัดคนละที่
