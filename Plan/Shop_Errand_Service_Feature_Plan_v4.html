2.3 บังคับ 2 ชั้น

  • ชั้น UI: ปุ่มยืนยันเป็น disabled พร้อมข้อความอธิบายเหตุผล + ปุ่ม "ลองตรวจอีกครั้ง"
  • ชั้น server: create_shop_booking() เรียก nearest_online_driver() ซ้ำ ถ้าไม่มีคนขับคืน error: 'no_driver_available' — กันทั้งการเรียก API ตรง และกันช่องว่างเวลาระหว่างเปิด dialog กับกดยืนยัน

ข้อจำกัดที่ต้องยอมรับ และทางรับมือ

การตรวจนี้ลดโอกาสสั่งแล้วไม่มีคนรับ แต่ไม่ได้รับประกัน — คนขับที่ว่างตอนตรวจอาจไปรับงานอื่นในวินาทีถัดมา หรือปิดแอปทันทีหลังลูกค้ากดยืนยัน ดังนั้น:

  • ยังต้องมี timeout หาคนขับ (shop_match_timeout_min, เริ่มที่ 10 นาที) แล้วคืน hold เต็มจำนวนอัตโนมัติ พร้อมแจ้งลูกค้า
  • ระหว่างรอคนขับ ต้องแสดงให้ลูกค้าเห็นว่ากำลังหาอยู่ และบอกว่าถ้าหาไม่ได้จะคืนเงินเต็ม — ไม่ให้ลูกค้ากังวลว่าเงินที่ถูกกันไปจะหาย
  • ห้ามสื่อสารกับลูกค้าว่า "รับประกันมีคนขับ" เพราะระบบทำไม่ได้จริง

5.2 เงินไม่พอ — จัดการใน dialog เดียวกัน

dialog สรุปราคา→ ตรวจพบยอดไม่พอ ขาด ฿X→ ปุ่มเปลี่ยนเป็น "เติมเงิน ฿X แล้วสั่ง"→ ไปหน้าเติมเงิน Beam→ กลับมา dialog เด้งเองพร้อมราคาใหม่→ กดยืนยัน
  • ยอดไม่พอ ให้แสดงบรรทัด "ขาดอีก ฿X" สีเตือน ใต้ยอด Wallet คงเหลือ
  • เติมเงินขั้นต่ำเท่าที่ขาด ปัดขึ้นตามขั้นต่ำของ Beam
  • เก็บ draft ไว้ในเครื่อง ก่อนออกไปหน้าเติมเงินทุกครั้ง — รายการของ ร้านที่เลือก ที่อยู่ส่ง วงเงิน ต้องอยู่ครบเมื่อกลับมา
  • เก็บ draft ที่ local ไม่สร้างแถวใน DB — ออเดอร์เกิดจริงตอนกดยืนยันเท่านั้น
  • กลับมาแล้ว ขอ quote ใหม่เสมอ เพราะคนขับและสถานะร้านอาจเปลี่ยนระหว่างนั้น
ทำไม draft ยังจำเป็นทั้งที่เป็น dialog: ถึง dialog จะไม่เปลี่ยนหน้า แต่การไปเติมเงินต้องออกจากแอปไปหน้า Beam จริง ซึ่งระบบปฏิบัติการอาจคืน memory ของแอประหว่างนั้น ถ้าไม่เก็บ draft ลงที่เก็บถาวรในเครื่อง ลูกค้าอาจกลับมาเจอรายการที่พิมพ์มาหายทั้งหมด

5.3 อายุของราคา

  • quote มีอายุ shop_quote_ttl_sec (เริ่มที่ 120 วินาที) เก็บ quote_token + quoted_at
  • หมดอายุแล้วกดยืนยัน → ขอราคาใหม่แล้วแสดงให้ดูอีกครั้ง
  • create_shop_booking() คำนวณซ้ำเสมอ ถ้าต่างจากที่แสดงไป → คืน error พร้อมราคาใหม่ ไม่ใช่เงียบ ๆ คิดราคาใหม่

6.2 จุดที่ต้องระวังตอนเขียน

  • ค่าปรับต้องคำนวณจาก snapshot ที่เก็บตอนสร้างออเดอร์ ไม่ใช่จาก config ปัจจุบัน — ลูกค้าที่สั่งตอนเพดาน 100฿ ต้องไม่โดน 150฿ เพราะแอดมินแก้ค่าระหว่างที่ออเดอร์กำลังทำอยู่
  • การโอนค่าปรับให้คนขับต้องอยู่ใน transaction เดียวกับการคืนเงินลูกค้า ถ้าครึ่งทางล้ม เงินจะหายไปจากระบบ
  • ค่าปรับเข้าคนขับต้องไม่นับเป็นรายได้ที่หักค่าคอม เพราะเป็นค่าชดเชย ไม่ใช่ค่างาน — ต้องแยก type ใน ledger ให้ชัด ไม่งั้นรายงานรายได้จะเพี้ยน
  • ต้องกันคนขับสมคบ — คนขับกด "ถึงร้าน" แล้วชวนลูกค้ายกเลิกเพื่อแบ่งค่าปรับ ทำได้ในทางทฤษฎี → geofence ในหัวข้อ 4 ช่วยได้ส่วนหนึ่ง และควรมีรายงานให้แอดมินเห็นคนขับที่มีอัตราการถูกยกเลิกตอน shopping สูงผิดปกติ

6.3 คำเตือนก่อนยืนยัน

  • แสดงใน dialog สรุปราคา (หัวข้อ 5) เป็นจำนวนเงินจริงที่คำนวณแล้ว ไม่ใช่ "25%"
  • บอกด้วยว่ายกเลิกก่อนคนขับถึงร้านไม่มีค่าใช้จ่าย ไม่ใช่เขียนแต่ข้อเสีย
  • ครั้งแรกที่ใช้บริการเป็น dialog ต้องกดรับทราบ เก็บ ack_shop_cancel_policy_at ในโปรไฟล์ ครั้งถัดไปเป็นข้อความในสรุปราคาพอ

7.1 กฎ

  • นับเฉพาะ booking ที่ service_type='shop' และ status='completed' ของคนขับคนนั้น
  • ออเดอร์ที่วงเงินเกินเพดาน ไม่แสดงให้คนขับใหม่เห็นเลย ไม่ใช่ให้เห็นแล้วกดรับไม่ได้
  • เช็คซ้ำที่ server ตอนกดรับงาน กันการเรียก API ตรง
  • หน้าโปรไฟล์คนขับแสดง "ทำอีก N งานเพื่อรับงานวงเงินสูงได้"

7.2 แอดมินปลดล็อกด้วยมือ

  • เพิ่มคอลัมน์ profiles.shop_trusted_driver (boolean, default false)
  • เป็น true → ข้ามเพดานคนขับใหม่ทันทีไม่ว่าจะทำงานมากี่ครั้ง
  • อยู่ในกลุ่มคอลัมน์ที่ลูกค้า/คนขับแก้เองไม่ได้ — ต้องอยู่ใน guard เดียวกับ role/approval_status บทเรียนจากช่องโหว่ privilege escalation ผ่าน profiles ที่เคยแก้ไปแล้ว
  • ทุกครั้งที่แอดมินเปลี่ยนค่านี้ต้องบันทึกว่าใครเปลี่ยนและเมื่อไหร่
จำเป็นจริงตอนเปิดบริการ: วันแรกทุกคนเป็นคนขับใหม่หมด ออเดอร์เกิน 500฿ จะไม่มีใครรับได้เลย — แอดมินต้องตั้งคนขับชุดแรกเป็น trusted ก่อนเปิด shop_enabled ไม่งั้นบริการจะดูเหมือนเสีย
