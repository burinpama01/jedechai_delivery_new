1ตรวจคนขับออนไลน์ก่อนยืนยันสั่ง (Q8)

ข่าวดี: ของเดิมมีอยู่แล้วบางส่วน — FareAdjustmentService.findNearestOnlineDriverDistanceKm() ใน lib/common/services/fare_adjustment_service.dart ทำสิ่งนี้อยู่แล้วสำหรับบริการเรียกรถ ไม่ต้องเขียนใหม่จากศูนย์ แต่ต้องยกระดับ (หัวข้อ 1.3)

1.1 ของเดิมทำงานยังไง

findNearestOnlineDriverDistanceKm(pickupLat, pickupLng, vehicleType)
  1. อ่าน driver_locations  WHERE is_online = true AND is_available = true
  2. join profiles          WHERE is_online = true
                              AND approval_status = 'approved'
                              AND vehicle_type ตรงกับที่ขอ
  3. ตัดพิกัด (0,0) ทิ้ง  (คนขับที่ยังไม่เคยส่งตำแหน่ง)
  4. คืนระยะทางของคนขับที่ใกล้ที่สุด (กม.) หรือ null ถ้าไม่มีใครเลย

มีคู่กับ config ride_far_pickup_threshold_km + ride_far_pickup_rate_per_km_motorcycle|car สำหรับคิดค่าวิ่งไกล ซึ่งเป็นแนวคิดเดียวกับ QQ เป๊ะ

1.3 สิ่งที่ต้องยกระดับ สำคัญ

ปัญหาของ logic เดิม: คำนวณฝั่ง client (Dart) ทั้งหมด ซึ่งมี 3 ข้อเสีย:

  1. ขัดหลักการ Batch 1 ที่ตั้งไว้ว่าเงินทุกบาทต้องคำนวณฝั่ง server — ถ้าค่าวิ่งไกลคิดที่แอป แอปที่ถูกดัดแปลงก็ส่งราคาที่ต้องการมาได้
  2. ดึงตำแหน่งคนขับทุกคนที่ออนไลน์มาที่เครื่องลูกค้า เป็นการเปิดเผยตำแหน่งคนขับทั้งระบบให้ client เห็น ทั้งที่ต้องการแค่ระยะทางตัวเลขเดียว
  3. โหลดหนักขึ้นเรื่อย ๆ เมื่อคนขับเยอะ เพราะดึงมาทั้งหมดแล้วค่อยกรองที่เครื่อง
ทางแก้: ย้ายไปเป็น RPC ฝั่ง server ตัวใหม่ nearest_online_driver_km(p_lat, p_lng, p_vehicle_type, p_service_type) ที่คืนเฉพาะ { distance_km, driver_count_in_radius } — ไม่คืนตำแหน่งหรือตัวตนคนขับเลย จากนั้นให้ฝากซื้อใช้ตัวใหม่ตั้งแต่แรก และทยอยย้าย ride/parcel มาใช้ทีหลัง (ไม่แตะของเดิมในรอบนี้ เพื่อไม่ให้กระทบ vertical ที่ใช้งานจริงอยู่)

1.4 ผลลัพธ์ที่เป็นไปได้ 3 แบบ และ UI ที่ต้องแสดง

สถานการณ์แสดงอะไรสั่งได้ไหม
มีคนขับในรัศมี"มีคนขับ N คนในพื้นที่" · คิดราคาปกติได้
ไม่มีในรัศมี แต่มีคนขับใกล้สุดนอกรัศมีเตือนว่ามีค่าวิ่งไกลเพิ่ม X บาท (หัวข้อ 2.2) + บอกระยะได้ ถ้ายอมรับค่าเพิ่ม
ไม่มีคนขับออนไลน์เลย"ตอนนี้ยังไม่มีคนขับว่างในพื้นที่ ลองใหม่อีกครั้งภายหลัง"ไม่ได้
ข้อจำกัดที่ต้องยอมรับ: การตรวจนี้ลดโอกาสสั่งแล้วไม่มีคนรับ แต่ไม่ได้รับประกัน — คนขับที่ว่างตอนตรวจอาจไปรับงานอื่นในอีก 10 วินาทีถัดมา ระบบจึงยังต้องมีเส้นทางรองรับกรณีไม่มีคนรับงานอยู่ดี (timeout แล้วคืน hold เต็มจำนวน) อย่าเข้าใจผิดว่าฟีเจอร์นี้แทนที่การจัดการกรณีหาคนขับไม่ได้

2.2 สูตรค่าวิ่งไกล

d = ระยะทางจากคนขับที่ใกล้ที่สุด (ออนไลน์ + ว่าง) ไปยังร้าน
R = shop_driver_to_store_km        (รัศมีปกติ, แอดมินตั้ง)

ถ้า d <= R   =>  ค่าวิ่งไกล = 0                      (คิดราคาปกติ)
ถ้า d >  R   =>  ค่าวิ่งไกล = (d - R) x อัตราต่อ กม. ตามประเภทรถ
                  แล้ว clamp ไม่ให้เกิน shop_far_pickup_max_fee

2.3 คำนวณที่ไหน

ทุกตัวเลขในหน้าสรุปมาจาก RPC ตัวเดียว shop_quote(store_id, budget_cap, dest_lat, dest_lng, vehicle_type) ที่คำนวณฝั่ง server ทั้งหมด แอปแค่แสดงผล ไม่คำนวณเอง จากนั้นตอนกดยืนยัน create_shop_booking() คำนวณซ้ำอีกครั้ง แล้วเทียบกับที่แสดงไป — ถ้าต่างกันเกินเล็กน้อย (เช่นคนขับใกล้สุดเปลี่ยนไประหว่างนั้น) ให้แสดงราคาใหม่ให้ลูกค้ายืนยันอีกครั้ง ไม่ใช่เงียบ ๆ คิดราคาใหม่

อายุของ quote: เก็บ quote_token + quoted_at อายุ 2 นาที ถ้าลูกค้าค้างหน้าไว้นานกว่านั้นแล้วกดยืนยัน ให้ขอราคาใหม่

2.4 เงินไม่พอ → เติมทันที (Q1)

หน้าสรุปราคา→ ยอดไม่พอ: ขาดอีก ฿X→ กดเติมเงิน (Beam)→ เติมเสร็จ→ กลับมาหน้าเดิม ข้อมูลครบเหมือนเดิม→ กดยืนยันได้เลย
  • ปุ่มหลักเปลี่ยนจาก "ยืนยันสั่ง" เป็น "เติมเงิน ฿X แล้วสั่ง" โดยเติมเงินขั้นต่ำเท่าที่ขาด (ปัดขึ้นตามขั้นต่ำของ Beam)
  • ต้องเก็บ draft ออเดอร์ไว้ ระหว่างไปเติมเงิน — รายการของที่พิมพ์มา ร้านที่เลือก ที่อยู่ส่ง ต้องอยู่ครบเมื่อกลับมา ถ้าหายลูกค้าต้องพิมพ์รายการใหม่ทั้งหมดซึ่งจะทำให้เลิกสั่งไปเลย
  • เก็บ draft ในเครื่อง (local) ไม่ต้องสร้างแถวใน DB — ออเดอร์เกิดขึ้นจริงตอนกดยืนยันเท่านั้น
  • กลับมาแล้วต้อง ขอ quote ใหม่ เพราะเวลาผ่านไป คนขับและสถานะร้านอาจเปลี่ยน

4ยกเลิกกลางคัน หัก 25% (Q3)

4.1 กฎ

ยกเลิกตอนสถานะคืนเงินเหตุผล
pending (ยังไม่มีคนรับ)คืนเต็ม 100%ยังไม่มีใครเสียเวลา
accepted (คนขับรับแล้ว ยังไม่ถึงร้าน)คืนเต็ม 100%ยังไม่เกิดต้นทุนจริง
shopping (คนขับถึงร้าน/กำลังเลือกของ)หัก 25% ของยอด holdคนขับเดินทางไปแล้วและกำลังทำงานอยู่
receipt_review ขึ้นไปยกเลิกไม่ได้ของซื้อแล้ว คืนร้านไม่ได้ ต้องผ่านแอดมิน

4.2 คิด 25% จากอะไร — ต้องนิยามให้ชัดตั้งแต่ตอนนี้

"25% ของยอดที่ hold" ต้องระบุให้ชัด เพราะ hold = วงเงินสินค้า + ค่าบริการ ซึ่งให้ผลต่างกันมาก:

วิธีคิดตัวอย่าง (hold 605฿ = ของ 500 + บริการ 105)ผล
25% ของยอด hold ทั้งก้อนหัก 151.25฿ตรงตามที่สั่งตามตัวอักษร แต่ค่าปรับผูกกับวงเงินที่ลูกค้าตั้ง — ตั้งวงเงินเผื่อเยอะแล้วโดนปรับแพงขึ้น ทั้งที่คนขับทำงานเท่าเดิม
25% แต่มีเพดานหัก 151.25฿ แต่ไม่เกิน 150฿กันเคสวงเงิน 5,000 บาทแล้วโดนปรับ 1,250 บาท

ข้อเสนอ: ใช้ 25% ของยอด hold ตามที่สั่ง แต่เพิ่ม shop_cancel_fee_max (เริ่มที่ 150฿) และ shop_cancel_fee_min (เริ่มที่ 20฿) เป็นตัวคุมสองด้าน ทั้งหมดแอดมินปรับได้ — ต้องการการยืนยันจากผู้ใช้

4.3 เงินค่าปรับไปไหน

ต้องตัดสินด้วย เพราะกระทบ settlement: เข้าคนขับทั้งหมด (ชดเชยคนที่เสียเวลาจริง) หรือแบ่งกับแพลตฟอร์ม
ข้อเสนอ: เข้าคนขับทั้งหมด เพราะเป็นค่าชดเชยเวลาของคนขับโดยตรง แพลตฟอร์มไม่ได้เสียอะไรในเคสนี้ และทำให้คนขับกล้ารับงานฝากซื้อมากขึ้น

4.4 คำเตือนก่อนกดยืนยันสั่ง

ก่อนยืนยัน โปรดทราบ
เมื่อคนขับถึงร้านและเริ่มเลือกของแล้ว หากคุณยกเลิก จะมีค่าชดเชยคนขับ 25% ของยอดที่กันไว้ (฿151.25)

และเมื่อคนขับชำระเงินที่ร้านแล้ว จะยกเลิกไม่ได้ เนื่องจากสินค้าคืนร้านไม่ได้

ยกเลิกก่อนคนขับถึงร้าน ไม่มีค่าใช้จ่าย

กฎของคำเตือน

  • แสดงจำนวนเงินจริง ไม่ใช่แค่ "25%" — ลูกค้าส่วนใหญ่ไม่คำนวณในหัว
  • อยู่บนหน้าสรุปราคา ก่อนปุ่มยืนยัน มองเห็นโดยไม่ต้องเลื่อน
  • บอกด้วยว่าเมื่อไหร่ยกเลิกฟรีได้ ไม่ใช่เขียนแต่ข้อเสีย
  • ครั้งแรกที่ใช้บริการให้เป็น dialog ต้องกดรับทราบ ครั้งถัดไปเป็นข้อความธรรมดา (ไม่งั้นน่ารำคาญจนคนเลิกใช้)
  • เก็บ ack_cancel_policy_at ในโปรไฟล์ เพื่อรู้ว่าเคยรับทราบแล้ว
ข้อควรระวังด้านความเป็นธรรม: ถ้าคนขับกด "ถึงร้านแล้ว" ทั้งที่ยังไม่ถึง ลูกค้าจะโดนค่าปรับทั้งที่ไม่ควรโดน → ควรให้สถานะ shopping เปลี่ยนได้ต่อเมื่อตำแหน่งคนขับอยู่ใกล้ร้านจริง (ในรัศมีที่ตั้งไว้) ไม่ใช่แค่กดปุ่ม

5ลูกค้าไม่ยืนยันรูปสินค้าใน 5 นาที (Q5)

ผู้ใช้เลือก: ไม่ auto-confirm — ครบ 5 นาทีแล้วให้แสดงช่องทางติดต่อคนขับโดยตรงแทน

5.2 ถ้าติดต่อกันไม่ได้เลย

ต้องมีทางออกสุดท้าย ไม่งั้นคนขับติดอยู่กับงานตลอดไปพร้อมของที่ซื้อแล้ว ข้อเสนอ:

  • ผ่านไป shop_photo_escalate_min (เริ่มที่ 20 นาที) นับจากส่งรูป → ออเดอร์เข้าคิวแอดมินอัตโนมัติ พร้อมธง "ลูกค้าไม่ตอบ"
  • คนขับมีปุ่ม "ติดต่อลูกค้าไม่ได้" กดแล้วส่งเข้าคิวแอดมินทันทีโดยไม่ต้องรอครบเวลา
  • แอดมินตัดสินได้ 3 ทาง: อนุมัติแทนลูกค้าให้ส่งต่อ / ให้คนขับเก็บของไว้แล้วคิดเงินตามจริง / ยกเลิกแบบพิเศษพร้อมระบุผู้รับผิดชอบค่าของ
  • ทุกการตัดสินของแอดมินต้องบันทึกเหตุผลไว้ — แบบเดียวกับ admin act-on-behalf ของ laundry ที่มีอยู่แล้ว

ทำไมใส่ตั้งแต่ตอนนี้ทั้งที่ยังไม่ใช้: multiplier ต้องถูก snapshot ลง fee_config_snapshot ตอนสร้างออเดอร์เหมือนค่าอื่น ๆ ถ้ามาเพิ่มทีหลังจะมีออเดอร์เก่าที่ snapshot ไม่มีฟิลด์นี้ ต้องเขียน fallback ไล่ทุกจุดที่อ่าน ใส่ตอนนี้ที่ค่า 1.0 ไม่เปลี่ยนพฤติกรรมอะไรเลย แต่พร้อมใช้ทันทีเมื่อต้องการ

หน้า Settings ใน Admin แสดงช่องกรอก multiplier ต่อหมวดไว้เลย พร้อมข้อความว่า "1.0 = คิดเท่ากับสูตรปกติ"
