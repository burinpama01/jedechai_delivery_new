3. วิธีที่ 2 — ราคาตลาดตามสถานะธุรกิจ

นี่คือส่วนที่ทำให้ราคาต่างกันได้ 5–10 เท่า ผู้ซื้อไม่ได้ซื้อบรรทัดโค้ด เขาซื้อ "เวลาที่ประหยัดได้" หรือ "รายได้ที่ได้ทันที"

สถานการณ์เงื่อนไขช่วงราคา (บาท)ผู้ซื้อคือใคร
A. ขายโค้ดล้วน
สถานะปัจจุบัน		 ยังไม่ขึ้น Play Store, ไม่มีผู้ใช้จริง, ส่งมอบ source + DB schema + เอกสาร 450,000 – 1,100,000 ผู้ประกอบการต่างจังหวัดที่อยากเปิดเดลิเวอรีเอง, agency ที่อยากได้ base
B. ขายพร้อมระบบที่เดินแล้ว ขึ้นสโตร์แล้ว มีร้าน 20–50 ร้าน คนขับ 10–30 คน ออเดอร์ประจำ แต่กำไรยังบาง 1,500,000 – 2,800,000 นักลงทุนท้องถิ่น, เจ้าของร้านอาหารรายใหญ่ในพื้นที่
C. ขายเป็นธุรกิจ มี GMV ต่อเนื่อง กำไรสุทธิพิสูจน์ได้ ≥ 12 เดือน 2–3.5 × กำไรสุทธิ/ปี กลุ่มทุน, คู่แข่งที่อยากได้ตลาด
D. ไม่ขายขาด — ทำ white-label
ผลตอบแทนสูงสุด		 ขายสิทธิ์ใช้งานต่อจังหวัด/ต่อเจ้า ไม่ผูกขาด 150,000–400,000 /ราย
หรือ 25,000–60,000 /เดือน		 ผู้ประกอบการหลายจังหวัด (ขายได้ซ้ำ)

ตัวอย่างคำนวณกรณี C (ให้เห็นภาพว่าต้องมี traction เท่าไรถึงจะคุ้มกว่าขายโค้ด)

สมมติ 100 ออเดอร์/วัน × ค่าเฉลี่ยบิล 350 บาท × ส่วนแบ่งแพลตฟอร์ม 20% = 7,000 บาท/วัน ≈ 2.55 ล้านบาท/ปี (รายได้แพลตฟอร์ม) หักต้นทุนดำเนินงาน/การตลาด/ซัพพอร์ต เหลือกำไรสุทธิ ~25–30% ≈ 640,000–765,000 บาท/ปี คูณ 2.5–3 เท่า → มูลค่ากิจการ 1.6–2.3 ล้านบาท บวกมูลค่าโค้ด

แปลว่า: ถ้ายังทำ traction ไม่ถึงราว 60–80 ออเดอร์/วัน การขายโค้ดล้วน (กรณี A) ตอนนี้ก็ไม่ได้เสียเปรียบมากนัก แต่ถ้าดันถึง 100+ ออเดอร์/วันได้ภายใน 6–12 เดือน มูลค่าจะขยับขึ้นเท่าตัว

ประเด็นระดับผลต่อราคาแก้อย่างไร
Service key ยังไม่ rotate critical ปิดดีลไม่ได้จนกว่าจะแก้ — ส่งมอบระบบพร้อมคีย์ที่อาจรั่วคือความรับผิดทางกฎหมาย rotate ทุกคีย์ (Supabase service key, FCM, SLIP2GO, LINE/Telegram token) + ตรวจ git history ว่าไม่เคย commit
Bus factor = 1 high −15 ถึง −30% เขียน runbook + วิดีโอเดินระบบ 2–3 ชม. + ระบุช่วง transition support (แนะนำ 30–60 วัน คิดค่าบริการแยก)
supabase db push ใช้ไม่ได้ (migration history desync) high −10 ถึง −20% repair migration history ให้ตรงกับ remote ก่อนส่งมอบ — ถ้าทีมใหม่ deploy ไม่ได้วันแรก ดีลพัง
ยังไม่ขึ้น Play Store (AAB target API 36 build แล้ว แต่ยังไม่ publish) high ตัดกรณี B/C ออกทั้งหมด publish ก่อนกำหนด 31 ส.ค. 2026 — แม้เป็น closed testing ก็ยังดีกว่าไม่มี listing
iOS ยังไม่พร้อม (มี Xcode project แต่ไม่มี GoogleService-Info.plist → push ใช้ไม่ได้) medium −10% แจ้งตรง ๆ ว่าเป็น Android-first และตี scope งาน iOS ให้ผู้ซื้อเห็น (ประมาณ 1.5–2.5 เดือน)
ไม่มี CI/CD, มีแค่ 8 smoke tests medium −5 ถึง −10% ใส่ GitHub Actions แค่ flutter analyze + flutter test + build check ก็ช่วยภาพลักษณ์มาก

ค่าใช้จ่ายบุคคลที่สามผูกติดมา info ต้องเปิดเผย ทำตารางต้นทุนจริง/เดือน: Supabase, Google Maps API, Firebase, SLIP2GO, Netlify, Play Console

6. แพ็กเกจส่งมอบที่ควรเตรียม

ผู้ซื้อจ่ายแพงขึ้นเมื่อรู้สึกว่า "รับไปแล้วรันต่อได้เลย" ของ 9 อย่างนี้เพิ่มราคาได้จริงมากกว่าการเขียนโค้ดเพิ่ม

  1. Source code ครบทุกส่วน — Flutter app, admin-web, landing, supabase/ (migrations + functions), scripts/
  2. เอกสารสถาปัตยกรรม 1 หน้า — แผนภาพ: 5 แอป → Supabase (Auth/DB/Realtime/Storage) → Edge Functions → FCM/LINE/Telegram/SLIP2GO
  3. Runbook ปฏิบัติการ — deploy แอป, deploy admin-web (Netlify), deploy edge function (ต้องระบุ --no-verify-jwt สำหรับ notify-admin-events), รัน migration, ดู log, จัดการ cron
  4. เอกสาร DB — รายชื่อ ~40 ตาราง + 73 RPC พร้อมคำอธิบายสั้น ๆ ว่าอันไหนใช้ทำอะไร
  5. รายการบัญชี/บริการที่ต้องโอน — Supabase project, Firebase, Google Cloud (Maps billing), Play Console, Netlify, โดเมน, SLIP2GO, LINE OA, Telegram bot
  6. ตารางต้นทุนดำเนินงานจริง/เดือน — ตัวเลขจากบิลจริง ไม่ใช่ประมาณ
  7. คู่มือแอดมิน — วิธีอนุมัติร้าน/คนขับ, ตรวจสลิป, อนุมัติถอนเงิน, ตั้งค่า GP
  8. บันทึกความเสี่ยงที่รู้อยู่ (disclosure list) — เอาข้อ 5 ทั้งหมดใส่ให้ครบ การเปิดเผยเองช่วยรักษาราคาได้ดีกว่าให้เขาไปเจอเอง
  9. ข้อตกลง transition support — 30–60 วัน คิดแยกจากราคาขาย (แนะนำ 30,000–60,000 บาท/เดือน)

7. คำแนะนำเชิงกลยุทธ์

ถ้าต้องการขายให้จบเร็ว (ภายใน 1–3 เดือน)

  • ตั้งราคาตั้งต้น 900,000 บาท ระบุชัดว่ารวมส่งมอบ + support 30 วัน
  • พื้นราคาที่ไม่ควรต่ำกว่า 450,000 บาท (ต่ำกว่านี้เท่ากับขายแรงงาน 6 เดือนในราคาต่ำกว่าเงินเดือนตัวเอง)
  • ก่อนเปิดขาย ต้องทำ 3 อย่าง: rotate คีย์ทั้งหมด, ซ่อม migration history, publish Play Store (แม้ closed testing)

ถ้ารับความเสี่ยงได้อีก 6–12 เดือน (ผลตอบแทนสูงกว่ามาก)

  • ดัน traction ให้ถึง ~100 ออเดอร์/วันในพื้นที่เดียว แล้วขายเป็นกิจการ → ขยับไป 1.5–2.8 ล้าน
  • หรือทำ white-label ขายสิทธิ์ต่อจังหวัด — ขายซ้ำได้ ไม่ต้องเสียสินทรัพย์ ผลตอบแทนสะสมมักสูงกว่าขายขาด

ถ้าเป้าหมายคือ "ส่งต่อให้คนอื่นบริหาร" (ไม่ขายขาด)

  • โครงสร้างที่เหมาะสุด: คุณถือสิทธิ์ IP ไว้ + ให้สิทธิ์ใช้งาน (license) + ส่วนแบ่งรายได้ 10–20% หรือค่า license รายเดือน
  • ข้อดี: คุณไม่ต้องบริหารประจำวัน แต่ยังได้ upside ถ้าเขาทำสำเร็จ และได้ระบบคืนถ้าเขาเลิกทำ
  • สิ่งที่ต้องมีก่อน: runbook + เอกสาร (ข้อ 6) และต้องแก้ bus factor ก่อน มิฉะนั้นคุณจะยังโดนตามแก้ระบบอยู่ดี
ข้อจำกัดของรายงานนี้ — ผมประเมินจากโค้ดและสถาปัตยกรรมที่ตรวจได้จริงเท่านั้น ยังไม่มีข้อมูล: จำนวนผู้ใช้จริง / ออเดอร์ต่อวัน / GMV / รายได้-กำไร / จำนวนร้านและคนขับที่ active / ต้นทุนจริงต่อเดือน ตัวเลขกรณี B และ C จะแม่นขึ้นมากถ้าให้ข้อมูลเหล่านี้ และรายงานนี้เป็นการวิเคราะห์มูลค่าสินทรัพย์ทางธุรกิจ ไม่ใช่คำแนะนำการลงทุนหรือการประเมินมูลค่าอย่างเป็นทางการโดยผู้ประเมินที่ได้รับใบอนุญาต
