เสนอ GP และเงื่อนไขค่าส่ง พร้อมติดตามผล

สถานะ: แบบเสนอเพื่อทบทวน ยังไม่แก้ runtime และยังไม่ deploy

ขอบเขตที่ผู้ใช้ยืนยัน

ร้านอาหารใหม่เลือกแพ็กเกจเดิม หรือเสนอ GP พร้อมเงื่อนไขค่าส่งเอง ต้องรอแอดมินอนุมัติ แสดงสถานะ มีการตีกลับพร้อมเหตุผล และปุ่มแก้ไขเสนอใหม่ เพิ่มคำอธิบายว่า GP คืออะไร

ร้านซักรีดยังคง flow เดิมตามระบบปัจจุบัน ข้อเสนอใหม่ไม่ใช้เปลี่ยนอัตราของร้านที่อนุมัติแล้วและมีเงื่อนไขใช้งานอยู่

ทางเลือกและข้อเสนอแนะ

วิธีผล
แยกข้อเสนอออกจากอัตราที่ใช้งานจริง — แนะนำเก็บประวัติและสถานะ ตรวจสิทธิ์ฝั่ง server อนุมัติแบบ transaction เดียว แล้วจึงบันทึกอัตราใน profile
เก็บข้อเสนอในช่องอัตราของ profileเสี่ยงใช้อัตราที่ยังไม่อนุมัติและแยกประวัติแต่ละรอบยาก จึงไม่เลือก

ต้นแบบ: ขั้นเลือก GP

เลือกเงื่อนไขของร้าน

GP คืออะไร?

GP คือค่าธรรมเนียมที่ระบบหักจากยอดขายอาหารตามเปอร์เซ็นต์ที่ตกลง เช่น ยอดอาหาร 100 บาท GP 10% หัก 10 บาท ร้านได้รับ 90 บาท ก่อนส่วนลดหรือรายการปรับอื่น ค่าส่งคิดแยกตามเงื่อนไขด้านล่าง

ตัวอย่างนี้ใช้เพื่ออธิบาย ยอดจริงอิงการคำนวณและการปัดเศษของระบบ

○ เลือกแพ็กเกจที่กำหนดไว้
● เสนอ GP และค่าส่งเอง

อัตราที่เสนอจะใช้หลังแอดมินอนุมัติเท่านั้น

ปุ่มในต้นแบบไม่ส่งข้อมูลจริง

ต้นแบบ: ติดตามข้อเสนอ

รออนุมัติ

ข้อเสนอรอบที่ 1

GP 10% · ค่าส่ง 10 บาท / 5 กม. · ส่วนเกิน 3 บาท/กม.

แอดมินกำลังพิจารณาข้อเสนอ อัตรานี้ยังไม่มีผลใช้งาน

สถานะเปิดร้าน: รออนุมัติร้าน

การอนุมัติข้อเสนอ GP ไม่อนุมัติเอกสารหรือเปิดร้านโดยอัตโนมัติ

ฝั่งแอดมิน

แสดงข้อเสนอล่าสุด ประวัติแต่ละรอบ GP และค่าส่งครบทุกช่อง ก่อนอนุมัติแอดมินต้องระบุส่วนแบ่ง GP ให้ระบบ/คนขับ โดยผลรวมตรงกับ GP ที่ร้านเสนอ

“อนุมัติข้อเสนอ” ยืนยันเงื่อนไขตามข้อเสนอ หากต้องปรับเงื่อนไขให้ตีกลับพร้อมเหตุผล ไม่แก้ตัวเลขแล้วอนุมัติแทนร้าน

“ตีกลับ” ต้องกรอกเหตุผล ร้านจึงแก้ไขจากข้อเสนอเดิมและส่งรอบใหม่ได้

สถานะและข้อกำหนด

สถานะสิ่งที่ทำได้
ยังไม่ส่งเลือกแพ็กเกจ หรือกรอกข้อเสนอพร้อมดูสรุปก่อนส่ง
รออนุมัติดูเงื่อนไขและเวลาที่ส่ง รีเฟรชสถานะ ไม่แก้ข้อเสนอที่อยู่ระหว่างพิจารณาและไม่ส่งซ้ำ
ตีกลับดูเหตุผลและประวัติ กดแก้ไขและเสนอใหม่ สร้างรอบใหม่โดยไม่เขียนทับรอบก่อน
อนุมัติแล้วแสดงเงื่อนไขที่อนุมัติ วันเวลา อัตราจริงจึงถูกบันทึก ร้านเปิดรับงานเมื่อการอนุมัติร้านผ่านด้วย

การเปลี่ยนกลับไปเลือกแพ็กเกจเดิมหลังตีกลับต้องทำอย่างชัดเจนและทำให้ข้อเสนอเดิมไม่ใช่รายการรอพิจารณาอีก ห้ามแอดมินอนุมัติข้อเสนอที่ไม่ใช่รอบล่าสุด

ข้อมูลและความปลอดภัย

เพิ่มตารางข้อเสนอและประวัติ พร้อมตัวชี้ข้อเสนอล่าสุดบน profile เพื่อให้ auth gate ตรวจว่าร้านส่งข้อมูลครบแล้ว แม้ยังไม่มี gp_plan_id ค่าสถานะและตัวชี้นี้แก้ได้ผ่าน RPC ที่ตรวจสิทธิ์เท่านั้น

ร้านอ่านเฉพาะข้อเสนอของตนและส่งได้เฉพาะร้านอาหารใหม่ แอดมินอนุมัติ/ตีกลับได้เท่านั้น RPC ล็อกแถว profile/ข้อเสนอ ป้องกันส่งซ้ำ อนุมัติซ้ำ และอนุมัติข้ามรอบ ห้าม client แก้อัตราที่ใช้งานจริงโดยตรง

ตรวจตัวเลขเป็น finite, GP 0–95% ตามขอบเขตเดิมของ gp_plans ค่าส่งและระยะทางต้องไม่ติดลบ เหตุผลตีกลับต้องไม่ว่างและจำกัดความยาว ฝั่งแอดมิน escape ข้อความจากร้านเพื่อป้องกัน XSS

การอนุมัติเปิดร้านผ่านทั้ง Admin Web และ Admin Flutter ต้องตรวจว่าข้อเสนอ GP ล่าสุดอนุมัติแล้ว หากยังรอหรือตีกลับห้ามเปิดร้านข้ามขั้นตอน

จุดที่ต้องแก้และทดสอบ

  • profile_completion_screen.dart และ profile_completion_policy.dart: ให้เสนอเองและผ่านไปดูสถานะได้โดยไม่ติดเงื่อนไข gp_plan_id
  • pending_approval_screen.dart และ gp_plan_service.dart: ดึงข้อเสนอล่าสุด แสดงสถานะ เหตุผล และเสนอใหม่
  • admin-web/src/pages/merchantsPage.js, admin-actions และ Admin Flutter: review ข้อเสนอพร้อมป้องกันเปิดร้านก่อนเงื่อนไขอนุมัติ
  • migration ใหม่: ตาราง, RLS, guarded profile metadata, submit/review RPC และประวัติแบบ transactional
  • ทดสอบ submit → pending → returned → resubmit → approved รวม owner/admin permissions, stale round, double submit, rejection reason, GP split และ auth gate
  • ทดสอบ UI: จอมือถือแคบ เหตุผลยาว ตัวเลขไม่ถูกต้อง โหลดผิดพลาด รีเฟรช และกลับมาเปิดแอปใหม่
  • code_reviewer หลัง implementation และ verification ก่อนสรุป พร้อมบันทึก Obsidian

หลักฐานและขอบเขตการยืนยัน

อ่าน source ของ GpPlanService, profile completion, pending approval, migration GP ปี 2026-07-16 และ cooldown ปี 2026-09-19 และค้นหา approval ฝั่ง admin แล้ว Graphify ที่มีอยู่ใช้เพียงภาพรวม เพราะ snapshot เก่ากว่า migration ล่าสุด SocratiCode ขึ้น fetch failed และผู้ใช้อนุญาตให้ใช้ rg/source โดยตรงแล้ว

ยังไม่แก้ code/config, ไม่ build/commit, ไม่ทดสอบ runtime, ไม่ deploy หรือรัน migration production จึงยังไม่ต้อง bump version หรือใช้ code_reviewer ในขั้นแบบนี้
